# 2026-11-13 Release 0.1.22: usage statistics say what failed, on which version and why

0.1.22 makes failed turns diagnosable from the usage statistics people already share: each failed turn now arrives
with its kind, model, the version that ran it and its error message scrubbed on the person's computer. It ships with
Haarness Cloud, which stores, keeps (90 days for what failed) and lists them for operators. CLI, Desktop and Haarness
Router (version only), Haarness for Chrome (version only) and Haarness Cloud with its workspace image are part of it;
the phones do not send usage statistics and are unchanged.

## What changed

- **Failed turns in usage statistics**: every failed turn of a day (its latest 50) with when it started, its kind from
  a closed list, provider and model named as the per-model counts name them, the Haarness version that ran it, the
  transcript's error message after scrubbing, and how far it got (duration, tool calls and errors, tokens, last tool).
- **Tool error messages**: what failed calls of Haarness's own file, search, web, task, skill, todo and workflow tools
  answered, scrubbed and grouped with how many calls said the same; a command's output, a page, a screen, a memory and
  an MCP server's or extension's words only count.
- **Turns by version**: turns now record the version that ran them, and each day reports its turns and failures per
  version, so a release's failure rate counts its own turns rather than an installation's latest version.
- **Scrubbing on the computer**: credentials as the logs lose them, then email addresses, paths and file names,
  addresses and hosts other than the public services Haarness talks to, IP addresses other than this computer's,
  numbers of nine digits or more and the names people gave their own providers and models. A hook's refusal is sent
  without its words. `haarness telemetry preview` shows each message exactly as it would be sent; Settings in Desktop
  (every language) and the terminal UI say that error messages are sent and what is taken out.
- **A refused key answered as a bad request** (Google's "API key not valid") now counts as `auth`, not
  `invalid_request`; running real failures through the report found it.
- **Cloud** stores failed turns, tool error messages and turns by version per day (migration 0564), keeps what failed
  90 days and the counts 400, and lists failed turns (`/internal/ops/telemetry/failures`, filterable by kind,
  provider, model, version, OS, installation and user) and tool error messages (`/internal/ops/telemetry/tool-errors`)
  for operators, with turns and failures by version in the usage totals. The privacy policy (effective 2026-11-13)
  and the data and storage guide say what is now sent and how long it is kept.

## Gate

Formatting and clippy `-D warnings` on both repositories; Rust workspace 3,848 passed (one OpenAI sign-in test lost
its fixed port 51880 to another sign-in on the machine, 3 of 3 alone); Desktop typecheck and 794 unit tests; the
release publish test; the boundary check on every repository. Cloud 1,208 Rust tests with Postgres (the identity,

Cloud API took a real report from a development build with three real failures (a Gemini key Google refused, a custom
endpoint that refused the connection, a read of a missing file), stored and listed them through the new operator
routes, and no stored row held the project, file, key or custom names. On staging the 0.1.22 release CLI sent the same
report and the rows read back with the version that ran each turn.

## Proof

- Production, 0.1.21 → 0.1.22: the macOS app launched through LaunchServices installed 0.1.22 itself and reopened;
  `FROM_VERSION=0.1.21 scripts/test-linux-update.sh` replaced the AppImage in place and reopened it on 0.1.22; the
  0.1.21 CLI showed "Haarness 0.1.22 is available" on its home screen and `haarness --update` installed it.
- Prod holds the three new tables; reports from 0.1.22 installations fill them as they send (every six hours).

## Not proven

Windows Desktop on a real Windows machine; Linux Desktop on a real machine; a real 0.1.22 installation's report
reaching prod (none had reported yet); GitHub Actions: the Cloud jobs do not start, and haarness main's test jobs on
Windows and Linux and the Desktop job on Linux failed before this change too; Haarness for Chrome 0.1.22 from the
Chrome Web Store (until the owner uploads it and review passes).
