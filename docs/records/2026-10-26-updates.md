# 2026-10-26 Updates: Desktop updates itself, the TUI says when one is out (0.1.6)

A desktop app should find a new version by itself, offer it in the sidebar and install it on request.
Haarness had only an electron-updater path that ran when `HAARNESS_UPDATE_URL` was set, which nothing set:
installed apps never looked for updates. This round adds both halves, against the release service
`install.sh` installs from, and ships them as 0.1.6. The owner asked for no `/update` slash command;
a `haarness --update` flag is the CLI's way in.

## What changed

- **Desktop** (`src/updates.ts`, `src/main/updater.ts`, `src/main/update-install.ts`,
  `src/renderer/Updates.tsx`): checks `/api/v1/releases/<channel>/desktop` 10 s after launch, every
  30 minutes and after a wake; downloads the file for this computer in the background (resume with
  `If-Range`, stall abort, fallback from the release domain to the service, size and SHA-256 checked;
  macOS: unpacked, version checked, `codesign --verify --deep --strict` and the requirement
  `anchor apple generic and certificate leaf[subject.OU] = "<running app's team>"`); stages it under
  `<userData>/updates`; **Restart to update** in the sidebar closes the windows, quits, and a detached
  helper swaps the app (old one moved aside until the new one is in place) and reopens it. A plain quit
  installs on macOS and Linux; Windows runs its setup (`--updated /S --force-run`) only after Restart.
  Settings → About shows the state, the one next step, release notes and why a check or download
  failed; **Download updates automatically** is on by default. Copies that cannot replace themselves
  offer Move to Applications or the installer. The electron-updater dependency and its code are gone.
- **TUI and CLI** (`crates/haarness-tui/src/updates.rs`, `view/home.rs`, `haarness-cli` `upgrade.rs`):
  a new chat's home screen shows `↑ Haarness X is available. · haarness --update` when the build's
  channel has a newer CLI for this platform (checked off the loop, at most every six hours, kept in
  `tui-state.toml`, off with `HAARNESS_NO_UPDATE_CHECK=1`, never in Desktop's bundled copy).
  `haarness --update` installs that release; it and `haarness upgrade` refuse to replace the
  `haarness` inside Desktop.
- **Docs**: `docs/DESKTOP.md#updates`, `docs/REFERENCE.md`, the release skill; haarness.ai's
  install, settings, TUI tour, CLI overview and troubleshooting pages (haarness-cloud 4d44578).
- `scripts/test-release-publish.py` errored in seven of nine tests since Windows signing added
  `--allow-unsigned-windows`; its arguments now include it.

An independent review of the first version found real bugs, all fixed with regression tests before
the release: failed downloads retried every minute forever (now 1, 5, 15 minutes, then 30, and a
damaged or wrongly signed file is not fetched again until the release changes); a release withdrawn
mid-download could still be installed; a newer release mid-download could start two writers on one
file; preview builds could be pointed at an older stable CLI; the team check read a self-declared
field and failed open; transient errors flickered a sidebar row; a cancelled restart could leave the
Windows setup armed.

## Verified

- Unit: Desktop 626 (updater 28, install 7, logic 3 among them), TUI 608, Rust workspace 2,595, SDK 32,
  Cloud web 388; `test-release-publish.py` 9/9.
- Desktop e2e, stand-in release service and stand-in installed app: a failed check then recovery,
  background download, Restart replacing and reopening; automatic downloads off with progress in the
  sidebar and a plain quit installing; a download damaged everywhere; Restart with unsaved file edits
  (Keep editing calls it off, every window and connection intact; saved, it restarts). Plus the
  startup/shutdown, settings, sidebar and settings-search specs (46 tests).
- TUI in tmux, stand-in service (`scripts/test-update-notice-tmux.py`): the notice, quiet on failure
  and on other platforms, kept between launches, off by environment, gone in a conversation;
  `--update` installs verified and refuses Desktop's copy.
- **Real releases.** A Developer ID–signed build labelled 0.1.4 updated itself from haarness.ai to
  0.1.5 (213 MB, ready in 28 s, swapped in 1 s, reopened). After publishing 0.1.6: a signed build
  labelled 0.1.5 updated from staging, then from prod, to 0.1.6 (ready in 19 s); the swapped-in app
  is "Notarized Developer ID" and satisfies the team requirement (a wrong team fails it); the updated
  app read the install result, cleaned its updates folder and says "You are up to date". A 0.1.5 CLI
  showed `↑ Haarness 0.1.6 is available` on the home screen and `haarness --update` installed 0.1.6.

## Release 0.1.6

Source c3e08a43 (tag v0.1.6), stable channel, release ID 01a178b4-cd52-75d5-9465-67ab3e444724, GitHub
release with 19 assets. Cloud 20261026-4d44578 and workspace image 20261026-c3e08a4-4d44578 in staging
then prod (haarness-deploy c586382). All six platforms built on this Mac (macOS natively, signed,
notarized and stapled, Gatekeeper accepted the app in the DMG and in the ZIP; Linux and Windows in
Docker with their platform checks); Windows unsigned, as for 0.1.5. The prod manifest serves CLI 0.1.6
(6 files), Desktop 0.1.6 (10) and Haarness for Chrome 0.1.6 (2); a fresh `install.sh` gives both.

## Left for a decision

- Windows: the update path (setup with `--updated /S --force-run`) has not run on a real Windows
  machine; the Linux AppImage swap and the .deb's installer path are covered by unit tests only.
- Desktop 0.1.5 and earlier have no updater: their users install 0.1.6 once by hand.
