# 2026-10-28 Release 0.1.10: Cloud credits that read right everywhere

0.1.10 is about Haarness Cloud credits. Every Cloud reply first holds its worst case and then settles to what it cost,
so a balance read during a reply dropped by hundreds of credits and came back. The TUI status band no longer shows
balances at all; `/billing`, Desktop, the web app and the phones count held credits as still there and name them
separately. Cloud also stops refusing replies its credits would cover, and no longer sends usage alerts or charges a
saved card because of a hold.

## What changed

- **Router**: a request's default output limit now also fits the credits the account can spend (included, and
  purchased with overage on). Sized for a model's full output, the hold could exceed what was left and refuse a reply
  that would cost a few credits; a 30k-token prompt to a frontier model needed a 2,013-credit hold on a 2,000-credit
  trial. A limit the caller sets is still never shortened.
- **Holds are not spending**: the 80%-used and used-up alerts and the automatic top-up sweep count held credits as
  left, so neither fires mid-reply.
- **Balances**: the account client sums each bucket's available and reserved credits; Desktop's sidebar counts
  purchased credits only when they can pay; purchased credits on hold are labelled; out of credits also covers
  purchased credits that wait for overage; a trial or a plan set to end says it ends rather than resets.
- **Advice**: a refused request says the credits cannot cover it, asks for overage when purchased credits are only
  waiting for it, and sends account and project budgets to Billing. Hooks see these refusals as `rate_limit`.
- **Checkout and plans** (Cloud): a new plan checkout expires the open one in Stripe, plan sessions close after 31
  minutes, a second subscription paid from a stale tab is recorded but never granted (an operator refunds it), the
  trial never starts beside a plan, an ended subscription is no current plan, turning overage off turns automatic
  top-ups off, a replayed trial event sends no refusal, and budgets follow the selected account.
- **Phones** (on main, not released): balances count held credits, a plan shows only under its own account, a trial
  ends rather than refills, a suspended account says so, and Android's refusals point at no purchase.

## Proof

- The worktree TUI in tmux against production: during a Sonnet reply `/billing` showed 903.57 credits with 400.07
  in use instead of dropping to about 500, then 834.67 once it settled; the status band showed no balance. The
  released 0.1.10 CLI showed the same panel.
- Router: a 30-credit balance and a model whose default output would need about 1,600 credits is admitted with a
  shorter limit (the test fails on the previous router); usage alerts and automatic top-ups each have a test with a
  hold of most of the balance that fails before the change.

## 0.1.9 → 0.1.10 on production

- **macOS**: a signed 0.1.9 app launched through LaunchServices offered Restart to update, installed 0.1.10 and
  reopened (`install result ok`).
- **Linux**: `FROM_VERSION=0.1.9 scripts/test-linux-update.sh` replaced the AppImage in place with the release's file.
- **TUI**: the 0.1.9 CLI showed the notice on its home screen and `haarness --update` installed 0.1.10.

## Not proven

Windows updates on a Windows machine, a Cloud workspace started on the new image, a live chat whose limit the router
shortened to fit a low balance (proven by the router test, not on production), the Desktop account dialog and the
changed web pages in a browser and the Android screens on a device (unit tests only; the iOS gallery screens were
checked in the Simulator), and Stripe's
expiry of an open Checkout session against live Stripe (the fixture and the route test only).
