# 2026-10-29 Release 0.1.11: Haarness Router ships with every release

Until 0.1.11 the only way to run Haarness Router yourself was to build it with Cargo, and that is what the website
told people to do. It now ships with every Haarness release on all six platforms and installs with one command. It
starts with nothing but provider keys in the environment, and its dashboard is in Haarness's own look. The website has
one router page for the hosted and the self-hosted router. The release also carries everything merged to main since
0.1.10.

## What changed

- **Router in the release**: product `router` beside the CLI, Desktop and Haarness for Chrome, at the release's
  version and built from the haarness-router tag of that version (`haarness-router-<os>-<arch>[.exe]`, the router's
  own commit recorded for each file). `curl -fsSL https://haarness.ai/install-router.sh | sh` and
  `irm https://haarness.ai/install-router.ps1 | iex` install it beside the CLI (`HAARNESS_PRODUCT=router` with the
  usual installers does the same); a download that is corrupt, unchecked or does not run leaves the previous one in
  place. The macOS router is signed and notarized like the CLI, the Windows builds link the C runtime statically, and
  its files also go to a GitHub release on haarness/haarness-router.
- **Router with no config**: it serves whichever providers have a key in the usual variables (OpenAI, Anthropic,
  Gemini or Google, Groq, Mistral, xAI, DeepSeek, Together, Fireworks, Bedrock). On a terminal it prints what it serves
  and where its dashboard is. It logs to stderr, as JSON when that is not a terminal, and says plainly when its port is
  taken. On a Linux system without CA certificates it says to install them, instead of failing on the first request.
- **Router dashboard**: redesigned in Haarness's colours and type, light and dark: a readiness badge, one searchable
  model picker, a playground whose answers stream in, options behind one button, and a key field only when the router
  needs one; the traffic, models and providers views follow the same design.
- **A router without provider keys** connects, and Haarness says to set a key where the router runs; its models then
  appear without connecting again (CLI, TUI, Desktop).
- **Website and docs** (Cloud): one `/product/router` page with a Hosted / Self-hosted switch (the old self-hosted
  page redirects there), the curl install on that page, on Download and in the docs, and pictures of the real
  dashboard.
- **Merged to main since 0.1.10**: marketplace installs and Git plugin marketplaces update by themselves (Desktop
  lists marketplaces with Update and an automatic-update switch); an MCP server slow to start no longer holds up a
  chat or an editor's prompts, and its start survives a client that gives up on it; @ completion waits for slow
  searches without blocking keys; a request too large for the provider says what to do; sign-in files stay out of
  prompts, instruction files and file tools; a tool that fails in the model's turn runs PostToolUseFailure; a refusal
  the server words in plain text reads as its own sentence, and a wrong token or password says it was refused.

## Proof

- Before the release, with the merged code: the router started with only OpenAI, Anthropic and Gemini keys in its
  environment, its dashboard answered from gpt-5-nano in the playground, and Desktop connected to it and ran a turn
  with a read tool through it; the CLI and TUI connected to it and to one without keys.
- `curl -fsSL https://haarness.ai/install-router.sh | sh` and the CLI's `install.sh` on this Mac (the router
  notarized with Developer ID) and in stock Ubuntu 22.04 on amd64 and arm64, where the router started with only a
  provider key and served its health check and dashboard.
- The released router with no config file and the three real keys: 3 providers, 112 models. The released CLI
  connected to it (`Connected router · 112 models available`) and got the exact reply asked for from
  `router/openai/gpt-5-nano`, `router/anthropic/claude-haiku-4-5-20251001` and `router/gemini/gemini-3.5-flash-lite`,
  and Claude Haiku read a file with its read tool through the router to answer.
- haarness.ai: `/install.sh` and `/install.ps1` are the repository's files, and `/install-router.sh` and
  `/install-router.ps1` differ from them only in the default product; `/product/haarness-router` redirects to
  `/product/router#self-hosted`; Download shows Haarness Router 0.1.11 with its install command; neither page scrolls
  sideways at phone width.

## 0.1.10 → 0.1.11 on production

- **macOS**: a signed 0.1.10 app launched through LaunchServices offered Restart to update, installed 0.1.11 and
  reopened (`install result ok`).
- **Linux**: `FROM_VERSION=0.1.10 scripts/test-linux-update.sh` replaced the AppImage in place with the release's file,
  and the app reopened with its flags and ran 0.1.11.
- **TUI**: the 0.1.10 CLI showed the notice on its home screen and `haarness --update` installed 0.1.11.

## Not proven

Windows on a Windows machine (the router and CLI ran under wine only; the PowerShell installer only in its container
tests), a paid request through the hosted router after this deploy (its health check answers and it refuses a request
without a key), providers other than OpenAI, Anthropic and Gemini through the self-hosted router (no keys here), and a
Cloud workspace started on the new image.
