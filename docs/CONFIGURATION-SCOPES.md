# Configuration and resource scopes

Where Haarness reads configuration and keeps its data, how global, system-folder and project layers take precedence, instruction files, Claude Code compatibility, and lifecycle hooks. For developers changing configuration loading, operators shipping team defaults, and anyone writing hooks.

> **User guides:** [Configure Haarness](https://haarness.ai/docs/cli/configuration), [Data and storage](https://haarness.ai/docs/security/data-and-storage).

Haarness separates user configuration, project overrides, persistent runtime data, transient cache, and application state. Desktop, CLI, TUI, daemon, and management tools resolve these locations through the CLI composition root; Electron does not own a separate agent configuration.

## Locations

| Content | Global | Project |
| --- | --- | --- |
| Configuration, permissions, provider definitions, MCP, hooks, tools, compaction and language settings | `~/.config/haarness/haarness.json` or `.jsonc` | `haarness.json{,c}` and `.haarness/haarness.json{,c}` |
| Agents and commands | `~/.config/haarness/{agents,commands}/` | `.haarness/{agents,commands}/` |
| Skills | `~/.config/haarness/skills/` | `.haarness/skills/` |
| Local plugin bundles | `~/.config/haarness/plugins/local/` | `.haarness/plugins/local/` |
| Extension registration and enablement | `~/.config/haarness/extensions.json` | `.haarness/extensions.json` |
| Discoverable extension source | `~/.config/haarness/extensions/` | `.haarness/extensions/` |
| Provider credentials | `~/.local/share/haarness/auth.json` | Never stored in project configuration by credential management |
| Conversations, project registrations, memory, schedules, plugin install records | `~/.local/share/haarness/` | Runtime records are keyed by workspace identity |
| Daemon discovery, leases and other disposable caches | `~/.cache/haarness/` | Workspace-specific subdirectories |
| Application state plane | `~/.local/state/haarness/` | Presentation state remains separate from agent configuration |
| Terminal UI client files: `tui-state.toml` (language, theme, thinking display, sidebar), prompt history (`tui-history-v2.json`), stash, saved servers and their drafts, `@` resource picks, themes | `~/.config/haarness/` | — |
| Chrome settings (`browser.chrome`) | `~/.config/haarness/haarness.json` or `.jsonc` | Can only tighten the global value; see below |
| Haarness for Chrome: host wrapper, copied binary, unpacked extension, opt-out marker (and the host manifest on Windows) | `~/.local/share/haarness/browser/chrome/` | — |
| Chrome upload staging | `~/.cache/haarness/browser/uploads/` | — |
| Native messaging host registration | Each browser's `NativeMessagingHosts` folder (macOS, Linux) or `HKCU` registry key (Windows) | — |

`XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_CACHE_HOME`, and `XDG_STATE_HOME` replace the corresponding base directories, including on macOS. Absolute `HAARNESS_HOME` puts the four planes beneath one root (`config`, `data`, `cache`, `state`). Explicit `--data-dir` / `HAARNESS_DATA_DIR` remains supported for existing isolated installations and test fixtures; either one also holds the server's preview versions, saved long tool output and workflow leases (`data/preview`, `data/tool-output`, `cache/workflow-leases`). On Unix the data folder (`data`, whichever root holds it) is made readable by its owner alone (0700). One already there is narrowed at every start, its group and other permission bits cleared, once it holds Haarness's files (`.layout-v1`, `workspaces.json`, `haarness.db` or `tool-output`), so the `worktrees/` in it are then private to its owner too; a folder of the person's that only has the name (`--data-dir ~` makes `~/data` the data folder) is left as it is until Haarness keeps its files there. The folders above it, the chosen root among them, are made as any folder is and never changed. The same goes for the folder the server keeps saved output and preview versions in when that is not the data folder (on a Mac without `--data-dir`, `~/Library/Application Support/dev.haarness.haarness`). Saved long tool output, long MCP resources and preview versions hold whole command output or pages, so `tool-output` and the preview folders are 0700 too and each file in them 0600. Without a home folder to find a data folder in, that output goes to `haarness-<uid>` in the system temp folder, made 0700: one already there that belongs to someone else, is a link or is open to others is passed over for a new `haarness-<uid>-<id>` of the process's own. A cargo test binary (`target/<profile>/deps/<crate>-<16 hex digits>`) that names none of these gets folders of its own under the system temp folder for those and for workflow leases, so a test never writes into the home of the person running it (checked by `tests_never_resolve_the_persons_own_data_folder` and the lease guard). Chromium window preferences, encrypted remote connection credentials and browser storage remain in Electron's native user-data directory; they are not project or agent configuration. Outside Haarness's own folders, `haarness browser setup` adds only the `ai.haarness.browser.json` host manifest to each browser's user-data folder (or a registry value on Windows); the extension keeps its own state in Chrome's extension storage. The wrapper it writes exports the absolute `HAARNESS_HOME`, `HAARNESS_DATA_DIR`, `XDG_CONFIG_HOME`, `XDG_DATA_HOME` and `XDG_CACHE_HOME` values in effect at setup, so a Chrome started from the Dock reaches the same roots. With a separate data folder (`--data-dir`, `HAARNESS_DATA_DIR` or `HAARNESS_HOME`), setup registers with the user's browsers only when given `--use-isolated-data-for-chrome`; test runs point it at a test profile with `--manifest-dir` or `HAARNESS_BROWSER_MANIFEST_DIR` instead. See [Haarness for Chrome](CHROME-EXTENSION.md#setup-and-data-layout).

## Precedence and management

Global settings load first (above the [system folder](#system-folder), when one is set), then project layers from the Git worktree root down to the selected workspace. Outside Git, the selected workspace is the boundary. Within each directory, Cloud workspace defaults in `.haarness/cloud/haarness.json` load first; regular project files can override them. Attached Cloud skill assets live in `.haarness/cloud/skills/`. This layer is also skipped by `--disable-project-config`. Within each directory, hidden `.haarness` configuration overrides root configuration. JSON overrides the matching JSONC file. Native Haarness resources override compatible resources; project resources override global resources with the same name. Singular `agent`, `command` and `skill` directories remain readable alongside plural directories. Without project configuration, Review also stops running the repository's own Git filters, looking inside changed submodules and fetching a partial clone's missing objects ([what a review runs](LARGE-DIFF-REVIEW.md#what-a-review-runs)).

Legacy `config.toml` remains readable and existing installations keep that format when managed in place. Its `[permissions]` rules apply in this order: the tool-wide entries (`edit = "ask"`), then each tool's table (`[permissions.bash]` or an inline `bash = { … }`); within each, a `"*"` catch-all first and the others as the file writes them. So `"*" = "allow"` written after `"echo secret*" = "deny"` never overrides that deny, and `"git push --force*" = "deny"` written after `"git push*" = "allow"` refuses `git push --force`. A `config.toml` that holds only `defaults` and `permissions` is migrated once to `haarness.json` (the old file kept as `config.toml.migrated`) with its rules written in that same order, so it decides as before; a `config.toml` whose permissions do not load (an action that is no action, a table where an action belongs) is not migrated and keeps refusing to load until it is fixed. Earlier builds read each table sorted by name, which put `"*"` first but also `"git push --force*"` before `"git push*"`; a `haarness.json` such a build migrated keeps the sorted order it wrote and is left as it is, so check that a narrower rule there still comes after the broader one it narrows. A `permission` action reads `allow`, `ask` or `deny` in any letter case (`"Deny"` is a deny) where it is written as a word: in `haarness.json`, `opencode.json` and an agent's `permission` map (a JSON agent entry or a Markdown agent's front matter), in `config.toml`, and in `haarness agent create --permission PATTERN=Deny`. There any other value leaves its rule out, with one warning in the log that names the file and the key (`config: ignored "permission.bash.rm *" in /path/haarness.json: "dney" is not allow, ask or deny`); `config.toml` and `--permission` refuse it, as before. An agent's permissions written as a list of `{"pattern", "decision"}` objects, and `browser.policy`, take the lowercase words only, as before. New provider/MCP settings use the scoped `haarness.json` file. JSONC management preserves unrelated comments and fields. Editing an existing provider or MCP server (Settings, the TUI, `haarness mcp enable/disable/edit`, `mcp_manage`) writes only the keys that changed, under the entry's own names and in its own shape: an `opencode.json` server keeps `type`, its `command` list, `environment` and `timeout` (milliseconds there, seconds in a Claude Code or plugin entry), and its OAuth settings stay in opencode's `oauth` object (`clientId`, a space-separated `scope`) or `oauth: false`, so opencode still reads it; a Claude-style server toggles `disabled`; a provider keeps settings the form does not show (context window, tools, key variables) and gains no defaults; keys Haarness does not know stay. A key written twice in the entry is refused (`"mcp.x.enabled" is written more than once …`), since the edit would land on the copy that is not read. In `config.toml`, values are kept but comments are not. Provider credentials remain global regardless of the scope of the provider definition, so a project cannot change the `base_url` of a built-in provider, a preset, or a provider defined in the global configuration: requests to that id carry the credential stored for it. Such a project entry is ignored with a notice (`Provider anthropic: ignored the project's base_url …`); give a project's own endpoint its own provider id. `haarness provider add` and the custom-provider forms in Desktop and the TUI refuse built-in ids for the same reason. Project permission rules follow global rules; agent restrictions and workspace-specific runtime approvals retain the engine's existing enforcement semantics. Chrome settings are the exception to project overrides: `browser.chrome` is read from the global layer, and a project layer can only turn Chrome off or make its site decisions stricter (allow → ask → deny); any deny in a layer's `browser.policy` also applies to Chrome, and `browser.policy.enabled: false` in any layer turns Chrome off. Desktop and the TUI always save Chrome settings globally. See [Chrome settings](BROWSER.md#chrome-settings). `auto_review` is the other: a project layer may only add `block` entries, which Auto's reviewer reads as untrusted, and lower `timeout`; its `enabled`, `model`, `environment` and `allow` are ignored with a notice, and its `small_model` sets its chats' default without choosing the reviewer (see [Auto's reviewer](AUTO-APPROVALS.md#autos-reviewer)).

Managed Chat Completions gateways can set `providers.<id>.server_output_limit = true` to let the server choose a budget-aware default output allowance. Ordinary providers keep their existing client defaults. An explicit request-hook output limit still reaches the server unchanged. Cloud workspace bootstrap enables this for its router provider.

Creating managed agents, commands, skills and plugins defaults to Global. Explicit Project scope writes within `.haarness`. Reads and edits resolve project before global when the scope is omitted; explicitly scoped operations only modify that scope. Extension settings now expose the same Global/Project choice. A project can override an inherited source without modifying another project's extensions. Executable project configuration continues to respect the existing project setting; the desktop enables it on opening a workspace.

Explicitly supported compatibility resources remain readable. These are imports, not Haarness-owned files: management does not rewrite the other application's credential/configuration stores. Plugin install records and fetched bundles remain runtime data, while user-authored local bundles belong to configuration. Profiles include portable resources from either scope and exclude credential stores and conversation databases.

## System folder

`HAARNESS_SYSTEM_CONFIG_DIR` names a configuration folder that sits under every other layer: a team's Git checkout, a folder device management installs, or the defaults a product ships. It has the global folder's layout and is read first, so the global folder, the project and everything above them override it. A system folder gives people a starting setup without taking anything away from them. Without the variable, or with an empty value, Haarness loads exactly as before. The value must be an absolute path: a relative one would name another folder for each process that reads it, so it is ignored, with one line on standard error (`HAARNESS_SYSTEM_CONFIG_DIR must be an absolute path; ignoring "team"`) and in the log. A server a client starts gets the client's resolved path.

```sh
HAARNESS_SYSTEM_CONFIG_DIR=/opt/acme/haarness haarness
haarness doctor   # … system config: /opt/acme/haarness
```

| Path in the system folder | What it adds |
| --- | --- |
| `haarness.json{,c}`, `opencode.json{,c}` | Settings with the global keys: model, providers, MCP servers, permissions, hooks, `instructions`, `skills`, compaction and the rest, merged in the global folder's file order |
| `AGENTS.md` | Instructions, before the global `AGENTS.md` |
| `agents/`, `commands/`, `skills/` (and the singular names) | Agents, commands and skills |
| `output-styles/` | Output styles |
| `prompts/` | [Prompt files](PROMPT-FILES.md) |
| `plugins/local/` | Local plugin bundles |
| `themes/` | Terminal UI themes |

`config.toml`, extension and plugin declarations (`extensions`, `plugin`, `plugins`), `extensions.json`, extension code, workflows and the switches Settings keeps in `capabilities.json` are read from the global and project layers only.

Settings merge from the system folder up, key by key: a global or project value replaces the system folder's, list keys such as `instructions` and `skills.paths` add to it with the system folder's entries first, and its permission rules come before the global ones, so a later rule still wins. Providers it defines count as global ones, so a project cannot change their `base_url`. An agent, command, skill, output style or theme with the same name in any other layer replaces the system folder's. Prompt files apply in folder order instead, the system folder's first (see [folders and precedence](PROMPT-FILES.md#folders-and-precedence)).

A system folder is trusted the way the global folder is: the person or program that starts Haarness names it, and a repository cannot. Haarness never writes into it, so it can be read-only. Settings, the terminal UI and `haarness` commands save to the global or project files; changing something that comes from the system folder saves the person's own version above it, as customizing a built-in agent does. Desktop's Edit on such an agent, command or skill saves a copy in the chosen scope; `haarness mcp disable <name>` (and Enable, Disable and Edit in Desktop and the terminal UI) first copies the server's entry in effect, as written, into the global configuration (or the project's with `--project`), only when no global or project entry already overrides it; turning the server back on removes that copy again when it is the system folder's entry apart from `enabled`, so later changes to the system folder reach the person; `haarness mcp remove` refuses and says to turn the server off instead. An agent's edit of any file in the system folder, like an edit of the global folder's `prompts/`, always asks a person, as for [Haarness's own configuration files](PERMISSIONS-AND-EXECUTION.md#haarnesss-own-configuration-files): no rule, Always answer, Auto, `--yolo` or schedule answers it. Its hooks are read-only in the hook editor, and its local plugins cannot be switched off or removed from Haarness. Entries of the system folder that a link leads into the project are not read, so a cloned repository cannot reach the base layer through one; the daemon log records `config: system folder entry not read: a link leads it into the project`. A system folder the variable itself names inside the project is read whole.

Items from the system folder carry a small **Base** tag in Desktop's Agents, Commands, Skills, MCP, Hooks and Plugins settings and in the terminal UI's lists, without Remove. `haarness doctor` prints the global configuration folder and `system config: <path>`, with `(not found)` when the folder is missing; a missing folder is also noted at startup. Hot reload watches the system folder's files as it does the global folder's. A server keeps the system folder it started with. A client started with the variable that finds the project's server reading another system folder, or none (compared where the folders really are, so a trailing `/` or a link makes no difference), replaces that server when it is idle, as it replaces one from an older build; while the server still has work in progress, the client uses it as it is and says once, on standard error and in the log, that the folder applies once that work is done. A client without the variable never replaces a server for this, so Desktop opened without it and a terminal with it do not take turns restarting the project's server; a manually started (open or password) server is never replaced, and the client says to restart it with the variable.

Apps opened from the Dock, the Start menu or a desktop launcher do not see variables set in a shell profile. Set the variable for the whole session instead:

- **macOS:** `launchctl setenv HAARNESS_SYSTEM_CONFIG_DIR /opt/acme/haarness` applies until logout; for every login, a LaunchAgent (`~/Library/LaunchAgents/`, or `/Library/LaunchAgents/` from device management) that runs that `launchctl setenv` command at load. Open Desktop again after setting it.
- **Windows:** System Properties → Environment Variables, `setx HAARNESS_SYSTEM_CONFIG_DIR "C:\Acme\Haarness"` for the user, or `setx /M` (or a Group Policy or Intune environment setting) for every user of the machine; sign out and in again.
- **Linux:** a `~/.config/environment.d/haarness.conf` line `HAARNESS_SYSTEM_CONFIG_DIR=/opt/acme/haarness` for systemd user sessions, or `/etc/environment` for every user; log in again. [Profiles](PROFILES.md#profiles-and-a-system-folder) never include the system folder.

## Instruction files

`AGENTS.md` in the global configuration directory loads first, then `AGENTS.md` from the Git worktree root down to the selected workspace. Each file may `@import` other files: bare `@docs/rules.md`, or `@"path with spaces.md"`, `@'path.md'` and `@<path.md>` for paths containing spaces; references inside fenced code blocks and inline code spans stay literal. Imports follow at most five hops, twenty files and 200 KiB per assembly, 40 KiB per file; project files cannot import from outside the workspace. Instructions load without asking anyone, so an import never reads a secret-named file (`.env`, `prod.env`; see [secret files](PERMISSIONS-AND-EXECUTION.md#secret-files)) or a file a configured `read` rule denies, judged by where a link really leads: `[Instruction import omitted: <path> (it is a secret file)]` or `(a read rule denies it)` takes its place. A remote instruction URL is named in the prompt and in notices without its user name, password or credential-named query parameters.

The `instructions` key in `haarness.json{,c}` and its legacy filename aliases appends more sources, in layer order:

```jsonc
{
  "instructions": [
    "docs/*.md",                        // glob, matched in the workspace and each ancestor up to the worktree root
    "~/shared/rules.md",                // home-relative
    "/opt/team/standards.md",           // absolute (globs allowed)
    "https://example.test/rules.md"     // fetched with a 10 s timeout, 200 KiB cap; failures are logged and skipped
  ]
}
```

Files under the global configuration directory or the supported home resource roots may import from outside the workspace; everything else is bounded like project `AGENTS.md`. Relative entries are ignored when project configuration is turned off.

When a `read` returns a file inside a workspace subdirectory, every `AGENTS.md` between that directory and the workspace root that the system prompt does not already carry is appended to the tool result once while the agent can see it (at most twenty files at a time, 40 KiB each). When compaction summarizes the result that carried a file, or an undo removes it, the next read below that folder appends the file again.

## Claude Code compatibility

Claude Code home and project files are never read unless a category is enabled:

```jsonc
{
  "compatibility": {
    "claude_code": {
      "instructions": true, // CLAUDE.md, .claude/CLAUDE.md, CONTEXT.md, *.local.md siblings and ~/.claude/CLAUDE.md
      "agents": true,       // .claude/agents/*.md (project walk-up) and ~/.claude/agents
      "commands": true,     // .claude/commands and ~/.claude/commands
      "skills": true        // .claude/skills and ~/.claude/skills
      // "enabled": false   // master switch: turns every category off
    }
  }
}
```

The same keys are accepted in TOML under `[compatibility.claude_code]`. With `instructions` on, each directory contributes the first family member that exists (`AGENTS.md`, then `CLAUDE.md`, `.claude/CLAUDE.md`, `CONTEXT.md`) together with its `.local.md` sibling; `~/.claude/CLAUDE.md` follows the global `AGENTS.md`, and lazy discovery on `read` includes the same family. Claude agent frontmatter is normalised: `tools` may be a comma-separated string or a list, `allowed-tools` stands in for a missing `tools`, colour names map onto the theme names (`red` → `error`, `green` → `success`, `yellow`/`orange` → `warning`, `blue`/`cyan` → `info`, `pink`/`magenta`/`purple` → `accent`, `gray`/`grey` → `secondary`), `model: inherit` means no pin, the `sonnet`/`opus`/`haiku`/`fable` families resolve at dispatch time to the newest release a provider lists (by version, so Sonnet 5.5 wins over Sonnet 5 whether ids end in a Bedrock `-v1:0`, a Vertex `@date` or a snapshot date), and a bare Claude id such as `claude-sonnet-5-5` resolves to that release in the provider's own spelling (`anthropic/claude-sonnet-5.5` on Haarness Cloud, `us.anthropic.claude-sonnet-5-5-v1:0` on Bedrock). Both prefer the chat's provider, then signed-in providers. Claude resources load before native ones, so a Haarness command, agent or skill with the same name wins. Every category is off by default, so existing installations behave exactly as before.

## Agent and command metadata

Markdown agents and `agent` entries in JSON accept the presentation and limit fields: `hidden` (kept out of pickers and `@` autocomplete), `color` (`#rrggbb` or a theme name), `steps`/`maxSteps` (provider/tool rounds before a final tool-free reply; overrides `tools.max_rounds` for that agent), `disable` (drops the agent, including one defined by an earlier layer), and `temperature`, `top_p`, `variant` (parsed and stored; not yet applied to provider requests). Command frontmatter and JSON `command` entries accept `subtask: true` as an alias of `context: fork`.

A turn reads its agent's definition once, when it is admitted (a delegated child: when it is dispatched), and keeps it until it ends: prompt, model, `steps`, `tools` and permission rules. Editing, renaming or deleting the agent from its file, the management tool, Desktop or the TUI changes the next turn, never a running one, so a running `reviewer` whose rules deny edits keeps denying them after its file is deleted. Work a running turn starts (a workflow agent, a direct tool on its child) takes its ceiling from that same definition. Edits to agent files made outside Haarness apply to new turns without waiting for other chats to go idle; see [hot reload](API.md).

Frontmatter that Claude Code accepts but YAML rejects is read the way Claude Code reads it: a top-level value with a colon and space inside it, such as `allowed-tools: Bash(git commit: *), Read`, is text, and so is an `argument-hint` made of bracketed placeholders, such as `[filename] [format]`. A value that opens a list or map (`tools: [Read, Grep]`), an alias, an anchor or a tag must still be valid YAML, so a malformed policy list fails instead of turning into text. A command, agent or skill whose frontmatter still does not parse is skipped and recorded in the daemon log as `config: skipped <command|agent|skill> <path>: <error>`; editing or customizing it from Haarness fails with that error and leaves the file unchanged.

Frontmatter is YAML between two `---` lines (an opening `---yaml` or `---yml` works too, and either fence may end in spaces) or a JSON object after an opening `---json`. Haarness never runs frontmatter as code: a file that opens with `---js`, `---javascript` or any other language is skipped the same way, with `JavaScript frontmatter is not supported` or `frontmatter language "…" is not supported`, rather than loaded without the tools, permissions or invocation limits it declares. A first line of four or more dashes is a horizontal rule, not frontmatter.

Inside a command template, `@path` references that name a workspace file are appended as bounded snapshots (128 KiB each, twenty per command); `@dir/` appends a one-level listing (200 entries); an `@name` that matches a visible subagent-mode agent and no file becomes the same delegation hint the TUI attaches. References inside code stay literal and paths outside the workspace are ignored unless written with `~/`.

## Skills from paths and URLs

```jsonc
{
  "skills": {
    "paths": ["./team-skills", "~/skills"],
    "urls": ["https://example.test/skills/"]
  }
}
```

`paths` are additional skill roots (`~/` and workspace-relative paths allowed; missing folders are skipped). Each `urls` entry names an index at `<url>/index.json` (or the `index.json` itself) of the shape `{"skills":[{"name":"…","description":"…","files":["SKILL.md", …]}]}`, with files fetched from `<url>/<name>/<file>`; an entry may instead point straight at its file with `"url"`. A skill name or file that would leave its folder (`..`, an absolute path, or `%2e%2e/`, which the address reads as `..`) is skipped. Fetches are best effort with a 10 s timeout; downloaded skills are cached under `~/.local/share/haarness/remote-skills/<host>/<name>/` and never refetched while present. Remote and path skills are listed after every native root, so a local skill with the same name wins.

## Message delivery preference

`input.delivery` in native Haarness JSON/JSONC files accepts `"steer"` (the built-in default) or `"queue"`. It is read from the global files and then the project layers, like other settings, and both clients change it through the server's `input-settings` management resource (`crates/haarness-cli/src/input_settings.rs`).

- **Desktop:** Settings → General → **Messages sent while working** is one **Steer | Queue** choice of what a message sent during work does in this project, with a caption naming where the value lives. Without a project override it is the global setting ("All projects"), and choosing changes it in the global `haarness.json{,c}`. **Override for this project** saves this project's own value in its `.haarness/haarness.json{,c}`, after which choices change only this project; **Use global setting (…)** removes it again, naming the value the project falls back to. Where a parent folder sets the value, the caption says **Parent folder** and a choice saves an override here, since the global setting would not reach it. With project configuration disabled only the global setting applies.
- **`/input-mode`** in either client (`steer`, `queue`, `toggle`, the default, or `reset`) changes only the current project, writing its `.haarness/haarness.json{,c}` without modifying an inherited ancestor. `/input-mode reset` removes the current directory's override and restores inheritance.

Saves are serialized by a lock in the global folder and keep unrelated keys and JSONC comments. This non-executable preference applies on the next submission, including during active work. See [Steer and Queue](INPUT-QUEUE.md) for commands and API examples.

## Interface language

The interface defaults to English on both clients, regardless of OS or terminal language. Use `/language` in either client, `/language en` to restore English, or Desktop Settings → General → Language. This is a saved client presentation preference, separate from project agent configuration: the TUI uses its saved state (then explicit `[tui].language` in application `config.toml`), and Desktop uses its local preferences. See [supported languages and translation behavior](../locales/README.md).

The TUI keeps such choices in `tui-state.toml` in the global configuration folder (`<data dir>/config` with `--data-dir` or `HAARNESS_DATA_DIR`). Each change reads, updates and rewrites the whole file, one change at a time, writing beside it and moving the result into place, so a read never finds it half written; when the file is a symbolic link (a dotfiles folder), the file it leads to is rewritten and the link stays (`write_whole` in `crates/haarness-tui/src/config.rs`). Files an earlier version kept in the platform folder (`~/Library/Application Support/dev.haarness.haarness` on macOS) are copied over once, without overwriting.

## Existing installations

On first use of the new layout, configuration and managed resources are copied from the former OS-specific directories without overwriting existing destinations. Credentials are adopted into the data plane. Migration markers prevent deleted settings or credentials from reappearing on the next launch. Source files are retained.

Existing data and cache directories are linked at their new canonical locations (a directory junction on Windows), rather than copying live SQLite databases, WAL files or daemon locks. This retains their identity and all concurrent writes; old absolute paths embedded in plugin registries stay valid. Fresh installations use ordinary directories. The compatibility links deliberately keep existing storage in place; no background data deletion is performed.

## Execution and remembered permissions

The native `execution` object supports configurable shell/Code Mode deadlines, media size, read concurrency, subagent concurrency/depth and exact observational extension exceptions for plan mode. Project overrides merge per field. See [Permissions and execution settings](PERMISSIONS-AND-EXECUTION.md) for defaults and examples, including explicit repository approvals shared across linked worktrees.

## Plugin and extension declarations

`haarness.json{,c}` and its legacy filename aliases accept the plugin and extension registration keys. Nothing is downloaded or cloned while configuration loads; the keys map onto Haarness's existing registration paths:

```jsonc
{
  "extensions": [
    "./extensions/reviewer",                      // path, relative to this file (file:// and ~/ also accepted)
    ["@team/reviewer@1.0.0", { "strict": true }]  // [spec, options]: options become context.options
  ],
  "plugins": [
    "reviewer@internal",                          // name@marketplace (or marketplace/name)
    { "spec": "linter@internal", "enabled": false }
  ],
  "plugin": ["example-notify", "docs@internal"]  // npm/path entries are extensions, name@marketplace entries are plugins
}
```

- **Extensions** (`extensions`, and `plugin` entries that are paths, `file://` URLs, `npm:` specs, scoped or versioned npm names) register through the same path as `extensions.json`. A path resolves relative to the declaring file and must name an extension file or package. An npm spec resolves to the newest package that `haarness extension install npm:<spec>` already installed; otherwise it is reported at startup as pending (`extension package X is declared in <file> but not installed; run haarness extension install npm:X`) because installing executes registry code and needs the network. Declared entries are enabled; an `extensions.json` entry for the same source wins, so `enabled: false` there still disables it. Declarations turn the extension system on unless an `extensions.json` file exists to say otherwise (`haarness extension disable` keeps winning). Project declarations require project trust, like every executable project setting.
- **Plugins** (`plugins`, and `plugin` entries of the form `name@marketplace` or `marketplace/name`) name marketplace bundles managed by `haarness plugin`. A declared plugin that `installed.json` does not contain is a pending install: it appears in `haarness plugin list` under "Declared in configuration but not installed" and in a startup notice with the exact `haarness plugin install <spec>` to run. `{ "spec": ..., "enabled": false }` hides an installed plugin from discovery (hooks, commands, agents, skills and bundled extensions) without rewriting the install record, and `haarness plugin list` shows it disabled.
- Entries that cannot be parsed are skipped with a notice naming the file and index; they never invalidate the configuration file.

The parser and mapping live in `crates/haarness-cli/src/config_specs.rs`; `extensions::sources` and `plugins::all_enabled_roots` consume them.

## Lifecycle hooks

The `hooks` object in any configuration layer (and `hooks/hooks.json` in a plugin bundle) runs shell commands at the lifecycle events listed below. Each handler receives one JSON document on stdin with `hook_event_name`, `cwd` and, where a thread exists, `session_id`; exit code 2 or a JSON `{"decision": "block"}` answer blocks the events that can be blocked. The document is written while the handler's output is read, both within its `timeout` (60 seconds by default), so a handler that never reads a large document, or prints much before reading it, still ends at its timeout; one that exits without reading it is fine, and an `async` handler never holds the turn.

A `command` runs through `sh -lc` from the project folder, with `HAARNESS_PROJECT_DIR`, `CLAUDE_PROJECT_DIR` and `OPENCODE_PROJECT_DIR` set to it (and `CLAUDE_PLUGIN_ROOT`, `HAARNESS_PLUGIN_ROOT`, `OPENCODE_PLUGIN_ROOT`, `CLAUDE_PLUGIN_DATA` and `HAARNESS_PLUGIN_DATA` for a plugin's hooks). The shell expands `${CLAUDE_PROJECT_DIR}` and the others itself, so inside double quotes a folder name with spaces, quotes or `$(…)` stays one value and never runs. Inside single quotes, where a shell expands nothing, a POSIX command gets `'"${CLAUDE_PROJECT_DIR}"'` (the quote closed, the value expanded in double quotes, the quote reopened), which stays safe even where Haarness misreads the quoting (a comment, a here-document, `$'…'`). A `shell: "powershell"` (or `pwsh`) command reads the placeholders as `${env:CLAUDE_PROJECT_DIR}` and so on; inside single quotes (ASCII or the curly U+2018–U+201B, which PowerShell also accepts) it gets the value itself only when the value holds nothing but letters, digits, spaces and `_ . / : \ -`, and otherwise the `${env:…}` text, which is then read literally rather than run. Every PowerShell statement that starts with a placeholder (at the start, after `;`, `|`, `&&`, `||`, `{` or a line break, or after the `&` or `.` operator) is called as `& "${env:CLAUDE_PLUGIN_ROOT}\gate.ps1" …`. A `command` with an `args` list runs without a shell and gets the values filled in, except the script argument of a program that is itself a shell (`sh`, `bash`, `zsh`, `dash`, `ksh`, `powershell`, `pwsh`, also behind `env NAME=value …`): the argument after `-c`, or after PowerShell's `-Command` in any accepted spelling (`-c`, `-com`, `/Command`, `-CommandWithArgs`, `-cwa`), is treated as above. Windows PowerShell 5's bare positional command, given without `-Command`, is not recognised and keeps the values filled in. `cmd` expands `%NAME%` before it reads `&`, so a `cmd /c` script keeps the value filled in; avoid placeholders there for folders whose names hold `&`.

The same rule covers the other shell text Haarness runs from configuration. An MCP server's `headersHelper` runs through `sh -lc` with the server's `env` (a plugin's server also gets its plugin root variables); its `${NAME}` and `${NAME:-fallback}` references are left for the shell to expand, as above (`'"${NAME}"'` inside single quotes), so on macOS and Linux a token or folder name holding `$(…)` is never run. On Windows each `${NAME}` (or `${NAME:-fallback}`) is written `%NAME%` for `cmd` to read from the helper's environment, where Haarness sets the value (the fallback when the variable has none), so no value, a secret least of all, appears in the helper's command line; as in any `cmd` command, a value holding `&` or `"` still splits the helper's command there. A command's or skill's `` !`…` `` snippet runs in the agent's shell with `CLAUDE_PROJECT_DIR`, `CLAUDE_SKILL_DIR`, `CLAUDE_PLUGIN_ROOT` (and its `HAARNESS_`/`OPENCODE_` spellings) and `CLAUDE_SESSION_ID` set in its environment, and its text keeps those references as written for the shell to read: a folder named `p$(touch x)` is a value, never shell text. As in any shell, a bare `${CLAUDE_SKILL_DIR}/run.sh` splits a folder name that holds a space into words, so quote it (`"${CLAUDE_SKILL_DIR}/run.sh"`); inside single quotes a reference is opened for the shell, with the quotes of `#` comments, `$'…'` strings and nested `$(…)` and `` `…` `` read as the shell reads them; in a quoted here-document (`<<'EOF'`), which expands nothing, a placeholder gets its value, and an unquoted one is left as written. Permissions judge the snippet with its folders filled in, as a person reads it: the approval card, rule matching, an Always answer and the outside-the-project check all see the real paths (`cat "${CLAUDE_SKILL_DIR}/../../x"` asks about the folder it leads to). A skill's `allowed-tools` name the filled-in paths only, so a command that sets `CLAUDE_PLUGIN_ROOT` itself never matches them; its `disallowed-tools` count in both spellings. On Windows, where the snippet runs in `cmd`, the values are filled into its text. Snippets are found in the definition as written, so a folder name holding `` !`…` `` never starts one. In a turn you start in Desktop, the terminal UI or an editor over ACP, a command waits for its snippets to finish, however long they take (a test suite, a build), and Stop ends them; everywhere else a snippet keeps the `execution.shell_timeout_ms` deadline: the iOS and Android apps, Haarness Cloud's web chat and schedules, `haarness run`, scheduled runs, the SDKs and other API clients (unless they send `attended`, see the [API](API.md)), and the turns Haarness starts itself, such as a background result or a `/loop` prompt. What a snippet prints goes into the prompt up to its last 2000 lines or 50 KB; past that, a line after it says so and names the file that keeps all of it. A snippet without a deadline could print until it is stopped (`npm run dev`, `tail -f`), so that file keeps only the first 64 MiB, and the line says so. The TUI hands its composer file to `$EDITOR` as a separate argument; the file is made new, readable by you only, in a folder of its own with a name no one can guess (the temporary folder is shared on Linux), and both go when the editor closes.

| Event | When | Payload beyond the common fields | Matcher compares |
| --- | --- | --- | --- |
| `SessionStart` | a chat is created; not a chat started inside another (a task subagent, a workflow's thread or agent), so a slow hook never holds up their first prompt | `source` (`startup`), `agent` | `source` |
| `UserPromptSubmit` | a root turn starts | `prompt` | — |
| `PreToolUse` / `PermissionRequest` | before a tool runs (the `question` tool too) / before the user is prompted | `tool_name`, `tool_input`; `PermissionRequest` adds `permission_patterns`, `allow_always` and, when that is true, `always_patterns` and `permission_suggestions` | tool name / the permission asked (`bash`, `edit`, `external_directory`, …); Claude aliases accepted |
| `PostToolUse` / `PostToolUseFailure` | after a tool finishes (an answered question too, with the answer as its output) | `tool_name`, `tool_input`, `tool_response`, `error` | tool name |
| `FileChanged` | after a successful `write`, `edit`, `multiedit` or notebook edit | `tool_name`, `tool_input`, `file_path` | tool name |
| `Stop` | a root turn completed | — | — |
| `PostCompact` | after a compaction commits | `trigger`, `compaction` | `manual` or `automatic` |
| `StopFailure` | once after terminal failure and exhausted recovery | `error` (`incomplete`, `content_filter`, `provider`, `tool`, `other`), `error_type` (what happened: `authentication_failed`, `rate_limit`, `overloaded`, `server_error`, `invalid_request` or `unknown` for a provider error; otherwise as `error`, and `unknown` for `other`), `error_details`, `provider_id`, `model_id` | `error` and `error_type`; also Claude Code's `billing_error` (a rate limit or quota) and `max_output_tokens` (a reply that ended early) |
| `TurnEnd` | after `Stop`, once per completed root turn | `turn_id`, `agent`, `provider`, `model`, `finish_reason` | — |
| `Notification` | a permission prompt is waiting (`permission_prompt`) or a turn completed (`turn_completed`) | `notification_type`, `message` | `notification_type` |
| `SessionEnd` | a thread is archived | `reason` (`archived`) | `reason` |
| `ConfigChange` | a hot-reloaded configuration generation became active | `source` (`reload`); no `session_id` | — |

A matcher is `*` (or empty), names separated by `|` (`Bash|Edit`; Claude Code's tool names are accepted), or a regular expression found anywhere in the value. Events marked — in the table have nothing to match: their matcher is ignored and the hook runs every time. Events that send only certain values (`SessionStart`, `SessionEnd`, `Notification`, `PostCompact`, `StopFailure`, `FileChanged`) never run a hook whose matcher matches none of them, such as a `SessionEnd` hook for `clear`; the Desktop editor and `/hooks` in the TUI mark such a hook **Never runs**. `StopFailure` keeps `error` as it always was, so a provider error is `provider` whatever went wrong, and adds `error_type`, which names it for what happened as Claude Code does: a rejected sign-in or API key (`authentication_failed`, also for HTTP 401 and 403), a rate limit or quota (`rate_limit`), an overloaded provider (`overloaded`, HTTP 529), another HTTP 5xx (`server_error`), a refused request, including one too long for the context window (`invalid_request`), or `unknown` when the message says nothing Haarness recognises. A matcher is compared with both, and with Claude Code's `billing_error` and `max_output_tokens` for what Haarness calls `rate_limit` and `incomplete`, so `provider`, `rate_limit` and `billing_error` all run for a rate limit.

`additionalContext` (top level or in `hookSpecificOutput`) from `UserPromptSubmit` reaches the model with that prompt: it is stored with the turn as a hidden message after the prompt, and later turns replay it as history. It is not added to the system prompt, so a hook that answers differently every turn does not rewrite the provider's cached prompt.

`tool_input` carries the tool's own arguments (`path`, `command`, …). For `PermissionRequest`, `tool_name` is the permission asked (`read`, `edit`, `bash`, `external_directory`, …) and `permission_patterns` what the prompt asks about. A file tool also asks about the file it really opens when links or `..` lead elsewhere, and the hook is asked about that file in a run of its own, with `tool_input.path` set to it: for a link `notes.txt -> .env`, the hook sees `.env`, not `notes.txt`. The prompt is answered only when every run allows it, and a deny in any run refuses it. For the same reason a `PreToolUse` allow, given for the path the tool names, never answers an ask about where that path leads. See [where a file really is](PERMISSIONS-AND-EXECUTION.md#secret-files). A `PermissionRequest` allow that carries an `updatedInput` (in `hookSpecificOutput`, or in `decision` as Claude Code writes it) approves other input than the call asked about, so it does not answer the prompt: the person is asked, and the call runs as the model wrote it if they allow it. Rewrite input in `PreToolUse`, which runs before the rules are checked.

A `PreToolUse` hook with the `question` matcher can answer the agent's question instead of you: it hands back the question's input with `answers` added in `updatedInput`, nobody is asked, and the agent gets that answer as if you had given it. The transcript shows the question with its answer and a quiet **Answered by hook** note, in Desktop and the TUI. A question call asks one question, so `answers` is `[["Unit tests"]]` (one list per question), `["Unit tests"]`, or Claude Code's object keyed by the question text (`{"Which test suite should I run?": "Unit tests"}`). A question that takes several answers takes several (`[["Cheese", "Basil"]]`, or `"Cheese, Basil"` in the object form), and they reach the agent joined with `, ` as Desktop joins them. Return `{}`, or nothing, to leave the question to the person; answers that do not fit (none, several for a question that takes one, more than one list, or one that is not a choice when the question allows no typed answer) are ignored with a log line, and the person is asked. Exit code 2 or a `deny` blocks the question as it blocks any tool, and a `PostToolUse` hook runs once it is answered, by a person or a hook, with the answer as its output. Claude Code's `AskUserQuestion` matcher matches it too. `answers` is never part of the question tool's own input, so the model cannot answer itself. An answer from a hook does not approve anything; use `PermissionRequest` for that.

```bash
# .haarness/answer-questions.sh, registered for PreToolUse with matcher "question"
jq 'if .tool_input.prompt == "Which test suite should I run?"
    then {hookSpecificOutput: {hookEventName: "PreToolUse",
          updatedInput: (.tool_input + {answers: [["Unit tests"]]})}}
    else {} end'
```

A `PermissionRequest` hook answers in `hookSpecificOutput.decision`: `{"behavior": "allow"}` allows once, `{"behavior": "deny", "message": "…"}` refuses, and `{"behavior": "allow", "always": true}` answers **Always**. Claude Code's form of Always is accepted too: an allow whose `updatedPermissions` holds an `addRules` entry with `"behavior": "allow"`, such as the `permission_suggestions` the hook was given handed back unchanged. Print nothing, or `{}`, to leave the prompt to the person; the prompt waits while the hook runs, so give a hook that asks someone elsewhere a `timeout` long enough.

```json
{ "hookSpecificOutput": { "hookEventName": "PermissionRequest", "decision": { "behavior": "allow", "always": true } } }
```

An Always answer remembers exactly what **Always** in the TUI remembers: the request's `always_patterns` (`git status *` for `git status --short`, the exact path for a read), for every chat on the running server until it stops, and the prompts already waiting that those rules cover are allowed with it. Whatever rules or `destination` a Claude Code `updatedPermissions` names, Haarness remembers its own patterns and writes nothing to disk, so a hook can never widen what it was asked about or leave a rule behind after it is removed. `allow_always` says whether the hook may answer Always; when it is false, an Always answer allows once. It is false for a request only a person answers (an edit of Haarness's configuration, a command Haarness could not read whole, a Cloud action that spends money), for Chrome and built-in browser site approvals, in a chat in Auto (which approves once and remembers nothing) and in a run nobody watches. When several hooks answer, Always holds only if every hook that allowed said Always, and a request asked about in several runs (a link and the file it opens) needs Always from each run.

Any other non-zero exit is a non-blocking error: the action continues and the daemon log records one `hook command failed` warning with the event, the chat it ran for (`session`), the command's program name, its exit code or signal and the start of its redacted stderr. Every block is logged once at INFO as `hook blocked`. The configured command line is never logged; see [observability](OBSERVABILITY.md#diagnostic-log-lines).

`SessionStart`, `SessionEnd`, `TurnEnd`, `Notification`, `FileChanged` and `ConfigChange` are observational: their output is logged, never applied. The desktop hook editor accepts these lifecycle events. `PostCompact` and `StopFailure` are observational: hook output never changes the compaction or retries a failed response. Cancellation does not emit `StopFailure`. JavaScript extensions receive the matching `session.start`, `session.end`, `session.compacted`, `chat.turn.failed`, `chat.turn.end` and `config` hooks; see [extensions](EXTENSIONS.md#hooks).

### Recovery and language-server limits

A provider that falls silent does not hold a turn: when a response sends nothing for five minutes (no text, and none of the keep-alive pings or comments providers send while they think), Haarness closes its request, so the provider stops generating, and says the provider sent nothing for 5 minutes, never that a connection was reset. The same limit covers the wait for the response to begin. Before any output the request is retried like an overloaded provider (up to four times, after 2, 4, 8 and 16 seconds); after partial output it is recovered like an incomplete stream below, continuing from what arrived. `/btw`, compaction summaries and titles have the same limit and fail instead of retrying. Set `providers.<id>.stream_idle_timeout` in seconds (`0` never gives up); a section without a `base_url` that only sets timeouts tunes a built-in provider or a detected local runtime without redefining it, and in a later configuration layer it tunes the earlier definition instead of replacing it. A provider on this machine (`localhost`, `127.0.0.0/8`, `::1`) waits as long as it takes unless configured: a local model sends nothing while it loads and reads a long prompt, which on a laptop can take far longer than five minutes, and a local server that dies closes its connection at once, so there is no silent network path to guard against. Amazon Bedrock's Converse answers in one piece, so silence until then is normal; it has `providers.<id>.request_timeout` instead, a limit on the whole answer (900 seconds by default, `0` waits as long as it takes), and reaching it fails the turn without a retry, since the answer may simply be long.

Incomplete provider streams retain partial text and usage and receive at most three recovery attempts per run. Empty responses retry the request; responses with partial output continue from durable history. Tools from an incomplete response are closed with an error instead of being executed, and completed earlier tool results remain in history. Incomplete-response recovery does not retry explicit provider errors or policy blocks. A response the provider's safety check stops (a content filter, a Bedrock guardrail, or Anthropic's `refusal` stop reason) fails the turn with code `provider_blocked` and says to send a follow-up message, rephrase the request or choose another model; text that streamed before the stop stays in the chat, and `StopFailure` hooks see it as `content_filter`. Every attempt contributes to usage accounting; context size remains based on the current conversation.

Gemini drops a function call it cannot parse, or one naming a tool it was not offered, and ends the response with `MALFORMED_FUNCTION_CALL` or `UNEXPECTED_TOOL_CALL`. Those responses count as incomplete rather than finished with an empty answer: the next request asks the model to continue, so it can issue the call again. Valid calls that arrived before the dropped one run as usual instead of being closed with an error, and only a response with no valid call uses up one of the three recovery attempts. `HAARNESS_BIN="$PWD/target/debug/haarness" python3 scripts/test-gemini-recovery.py` drives both cases, a discovered Gemini 4 model's thinking level and the region refusal below through a real daemon and TUI against a mock Gemini API.

A provider that refuses requests from this country or region (OpenAI's `unsupported_country_region_territory`, Gemini's "User location is not supported", Bedrock's "unsupported countries, regions, or territories") fails the turn at once, without retries, and says to choose a model from another provider.

Language servers stop after ten idle minutes by default. Configure `[lsp] idle_timeout_ms` and `max_clients` (default 6) to adjust retention per workspace daemon. Active operations, including diagnostic waits, are protected. At capacity, the oldest idle client is stopped; when all clients are busy, optional language work reports a capacity error. Reaped clients restart on demand without a failure backoff.

A subagent whose configured model is absent from its authenticated provider's catalog uses the parent's model and includes a substitution notice in foreground and background task results. A family or bare Claude id that no configured provider lists counts as absent. An explicit model argument takes precedence. Unknown providers and authentication/configuration errors are reported instead of triggering fallback.

A subagent's task result is its last reply in that run, never one from an earlier run of the same subagent (`task_id`) and never blank. A run that ended at the model's output limit says so ahead of its last text, with the output tokens when the provider reported them, or says it stopped before writing a reply; a run whose last step wrote no text says so, with the provider's finish reason, and hands on the last text it wrote before its final tool calls, which may be its answer (models often write it beside a last tool call, such as a todo update, and end with an empty step) or only narration; a run that wrote no text at all says it ended without writing a reply. When the provider's safety check stops a subagent, its parent is told plainly not to resume it or send the same task again (its history still holds what was blocked) but to rephrase or split the task, do the work itself or tell you, followed by any partial reply; the subagent's own chat keeps the message written for a person. A background subagent's result that a restart kept from its chat is delivered as the last reply its run stored, or says that it ended without writing a reply; a safety-check stop reads as above. How the run's last step ended is not kept over a restart, so that result does not say whether its run stopped at the output limit or wrote its text in an earlier step.
