Haarness is an AI assistant for working with code, files, and general tasks. Users open projects, create conversations, give the assistant work, watch streaming responses and tool activity, review changes, and use files or a terminal alongside chat. Multiple conversations can run independently. The app also provides models/providers, agents, commands, skills, plugins, MCP tools, workflows, schedules, goals, and settings. The existence of an engine capability does not mean it needs a permanent item in the main navigation.

The repository is `/Users/alex/work/haarness/haarness`; Desktop lives in `apps/desktop`. It uses Electron, SolidJS, TypeScript, Vite, and plain CSS with theme tokens. Electron's main process owns privileged desktop operations and the native voice helper; a narrow preload bridge connects it to the renderer. A Rust runtime owns conversations, durable history, tools, permissions, configuration, and execution. The desktop calls it through the TypeScript SDK and receives live events. CodeMirror powers the editor; xterm powers terminals. A separate TUI uses the same runtime, so desktop polish must preserve shared contracts and existing data.

Use precise product terminology. A project is a saved repository or folder. A worktree is a separate Git checkout belonging to that project. A conversation/session is a chat and its history, associated with its working location. Users can also chat without choosing a project; those conversations appear under Chats. Projects and conversations should feel continuously available. Runtime connection/reconnection is implementation detail, not a step users should manage. Global configuration applies across projects, with project-scoped resources kept separate; desktop appearance and layout preferences are a separate storage concern.

Keep these product expectations intact:

- The interface is simple. Secondary functionality belongs where it is useful, with progressive disclosure and direct actions. Avoid raw JSON settings forms, native HTML selects, action-selection dialogs, redundant controls, and success alerts for routine actions such as reordering.
- Projects can stay expanded independently. Project and session order is controlled by the user and persists; merely activating an item must not reorder it. Whole rows support dragging, with usable keyboard alternatives. Sidebar session rows have one archive action.
- New chat offers a searchable, anchored project picker, New project, and Don't work in a project. Preserve separate drafts and attachments across project/conversation switches. Worktree selection must clearly describe where work will run.
- Assistant messages expose small Copy and Fork icons on hover and keyboard focus, alongside compact timestamp metadata. User messages expose Copy only. Copy preserves the response text; a reply fork includes that reply and immediately appears in the correct conversation list. Forks have a quiet “Continued from [source title]” divider at the inherited-history boundary; activating it opens the original conversation at the source reply. Keep that provenance through reloads and renames.
- Delegations are compact task summaries with a description, agent/model, and live state. Clicking a summary opens its child conversation, which has a return-to-parent action and no chat or dictation input. Keep permission/question responses usable there. The sidebar shows independent parent conversations and forks; do not expose delegated child sessions there or mistake every `parentId` for a delegation. Activity uses text shimmer without a spinner, and the sweep must stay continuous across refreshes and remounts.
- Streaming respects the reader. Scrolling up pauses following; Jump to latest resumes it. Avoid layout jumps, overflow, unexplained outlines, hidden focus, and controls moving while being used.
- The send-button position becomes Stop while a task runs with no new draft. Keep the composer's activity treatment subtle. Voice input inserts editable text, never sends automatically, and stops when its conversation loses ownership.
- Permissions and questions belong to the conversation that needs them. They must not block navigation, another project's work, or the entire app. Errors should arrive promptly with a useful local recovery action.
- Support every palette in Light, Dark, and Auto. Use the shared theme tokens, accessible contrast, visible control focus, keyboard navigation, reduced motion, and layouts that work with narrow windows and side panels.
