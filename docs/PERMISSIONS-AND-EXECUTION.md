# Permissions and execution settings

How the permission engine decides, what an approval remembers, how shell commands and the scripts they run are read, which files and requests only a person can approve, and the execution budgets that bound tools and agents. For developers working on the runtime and clients, and for operators writing permission rules.

> **User guides:** [Permissions and approvals](https://haarness.ai/docs/security/permissions), [Execution budgets](https://haarness.ai/docs/security/execution-budgets), [Websites in your Chrome](https://haarness.ai/docs/security/permissions#websites-in-your-chrome).

Haarness uses one runtime policy for Desktop, attached TUI, CLI, workflows and nested tools. Ordinary workspace tools already run without approval. These settings reduce repeated prompts and let longer tasks finish while retaining explicit denials, cancellation and ordered writes.

## Choose what an approval remembers

- **Allow once** authorizes this request.
- **Always** in the TUI remembers it for every chat on the running server, until that server stops.
- **Always for this folder** persists it for the exact workspace.
- **Always for this repository** explicitly shares it with linked Git worktrees. In the TUI choose **Repository** (`r`), review the displayed rules, then press Enter.
- A `PermissionRequest` hook can answer **Always** as well; it remembers what the TUI's **Always** remembers, never on disk. See [lifecycle hooks](CONFIGURATION-SCOPES.md#lifecycle-hooks).

A website in the user's Chrome is the exception: it offers only **Allow once** and **Allow in this chat**, which lasts until the server stops and never applies to another chat. See [Chrome approvals](#chrome-approvals).

**A folder that holds the project.** An ask about a folder outside the project names that folder, and **Always** remembers all of it (`external_directory:/tmp/build/*`). A folder the project lies in (the home folder for `~/work/app`, or the project's parent) is asked about by the path the call names there instead, and **Always** remembers exactly that, since the folder would open everything beside the project for every later chat: after **Always** on `cat ~/.gitconfig`, that file is read without asking, while `cat ~/.ssh/id_ed25519` and `read ~/.netrc` still ask. A call that names the folder itself (`cd ..`, `list ~`, a `grep` of `..`) is asked about the folder alone (`external_directory:/home/me/`): **Always** then lets such calls run again, while every file in the folder still asks. A path there that may be any file in it, with a dynamic part or a wildcard (`cat ~/$f`, `cat ~/.n*`), is asked about the whole folder, as before: only a rule or an **Always** for all of it answers that, and the card says so. A line that runs in the folder, after a plain `cd ~` or `pushd ~` (followed as [Shell commands outside the project](#shell-commands-outside-the-project) describes) or with it as its `workdir`, is asked about the folder alone and about each file it then names there: `cd ~ && cat .gitconfig` asks for `~/` and `~/.gitconfig`, so **Always** on `~/.gitconfig` alone never lets a line run in `~`. A `cd` there that is not followed, such as a bare `cd` or `cd $HOME`, asks for the folder alone, and what the line names after it is read from the project. What a program does inside the folder by itself (a `grep` through it, `tar cf x.tar .`) is not read, as before. A rule for the folder (`"external_directory": {"~/*": "allow"}`), and an **Always** an earlier version saved for it, still cover everything in it.

In the TUI every choice that reaches past the one request (Always, This folder, Repository and Once + Auto) is staged first: the card names exactly what will be granted, and Enter, or the same key again once the card could be read, confirms. While the card has the keyboard only `y` (Allow once) and `n` (Reject) answer on one key. The key lights its chip at once and the answer is sent a moment later (300 ms) unless another key follows: a typed letter shows it began a message ("yes but…", "no wait"), and both go to the prompt with nothing answered. The same letter again, or Enter, sends it at once; Esc, Backspace or Ctrl+C takes it back; any other key (an arrow, Ctrl+Y, Ctrl+G) sends it first and then does its own thing. While it waits, the row under the chips says what is about to happen. The moment counts from when the terminal input read the keys, not from when the TUI got round to handling them, and a key, paste or click already sent when the moment ends is handled before the answer goes, so a slow moment never turns a reply into an approval. A letter answers only the request it was typed at: if another comes to the head of the card first (a session switch, another client's answer), the letter, a staged answer and the chip selection go with the old one. Any other key that is not an answer goes to the prompt, and letters the card took that turn out to start a message ("update…", "www…") move to the prompt without answering. Ctrl+G hands the keyboard to the prompt. On a Chrome card, `a` (Allow in this chat) answers on one key in the same way, because it reaches no further than this chat.

**Nothing on a card is invisible.** A card shows the characters a request carries that would not show, or would move the text around them, as muted codes: its command, path or address, the script it runs, the rules **Always** would save, the call's row in the transcript and, in the terminal UI, the one line the status row repeats. Desktop sets each code on a faint chip of its own and keeps it in one left-to-right piece in right-to-left text. `cat report`, a right-to-left override (U+202E) and `fdp.sh` read `cat report\u{202E}fdp.sh`, not `cat reporths.pdf`. This covers the control characters except tab and line feed (a carriage return too where a line ends: a shell keeps it as part of the word before it, so `cd dist` ending in CR LF goes into a folder whose name ends in a carriage return), direction marks, overrides and isolates, zero-width spaces and the other invisible format characters, tag characters, and the line and paragraph separators. What text needs stays as it is: the joiners U+200C and U+200D, the variation selectors of emoji and ideographs, the flags of England, Scotland and Wales, and Arabic signs such as U+06DD that draw a mark. In the lines an edit changes, only a direction override or isolate (U+202A–U+202E, U+2066–U+2069) is a code, so a changed line cannot be made to read as something else; the rest is the file's own text and reads as written. Only what is drawn changes; the request, the answer and the rules saved are exactly as sent. A script's text has a rule of its own (see [The script a command runs](#the-script-a-command-runs)).

A command (or path, or address) longer than the card's rows is read in place before it is answered: ↑/↓ and PgUp/PgDn scroll it, Ctrl+E expands it to every row the card can spare and back, and the row under it says which lines are on screen. That row appears only while there is more to see; the answers never leave the screen, however short the terminal, and scrolling keeps a staged answer staged. A terminal under 40 columns or 12 rows has no room for the card, so it shows the request in one line, a row of its answers with their keys, and the approval hint in the status row instead of "working"; the rows above them keep showing the newest of the conversation.

**Which call asks.** A request names the tool call that raised it as `callId`, on `GET /v1/permissions`, the `permission.requested` event and the turn's `waiting_permission` status (a batch's step as `<batch call id>:N`); a question names its call the same way (`GET /v1/questions`, `question.requested`, `waiting_question`). In a parallel group of reads the terminal UI marks each call a request names ⚠, keeps the spinner on a read still running beside it, and shows the calls after them ○ queued; a request not answered yet keeps its call ⚠ while a sibling's runs again. Desktop says **Needs approval** on that call only, and ACP clients get the request on it (a batch's step on its batch). An older server names no call: the terminal UI then takes the earliest call of the asking turn with no result, and Desktop every such call of it, as before.

## Auto's reviewer

In a chat in Auto, a reviewer model answers the requests that reach a prompt after rules, remembered answers, hooks and extensions: it approves once, blocks with a reason the agent reads, or leaves the request to a person with a note on the card. Haarness's own asks and whole-tool asks such as `"bash": "ask"` are reviewed; an ask configured for something narrower, such as `"bash": {"git push *": "ask"}`, goes to a person in Auto; requests only a person answers (Cloud spending and deletions, Chrome sites, Haarness's configuration files, reads and changes of [where Haarness keeps sign-ins](#where-haarness-keeps-sign-ins), unreadable shell lines) never reach it. `"auto_review": {"enabled": false}` restores Auto's earlier approve-once behaviour. See [Auto's reviewer](AUTO-APPROVALS.md#autos-reviewer) for what it sees, its settings, and how mode changes and Stop settle a request under review.

Repository consent uses the canonical Git common directory, never a remote URL or repository name. Independent clones and unrelated repositories retain separate approvals. Grants live in `repository-approvals.sqlite3` in Haarness's data directory. Existing folder approvals stay folder-scoped. A matching deny in the destination worktree remains effective. Non-Git folders offer folder/session consent only. Failed persistence keeps the prompt available to retry.

## Configure execution budgets

Use the global `~/.config/haarness/haarness.json{,c}` or a project's `.haarness/haarness.json{,c}`. Project fields override individual global fields. Existing TOML files accept the same keys in `[execution]`. Running work retains its configuration generation; subsequent work uses the reloaded configuration.

This example permits longer tools and two levels of task delegation:

```json
{
  "execution": {
    "shell_timeout_ms": 0,
    "subagent_concurrency": 6,
    "subagent_depth": 2,
    "read_parallelism": 8,
    "media_max_bytes": 20971520,
    "code_timeout_ms": 180000,
    "code_max_calls": 500,
    "code_max_source_bytes": 262144
  }
}
```

| Setting | Default | Meaning |
| --- | ---: | --- |
| `shell_timeout_ms` | 120000 | Default shell deadline in milliseconds; `0` disables it. A bash call can override it with `timeout`. A command that runs without a deadline saves only the first 64 MiB of its output. A command's or skill's `` !`…` `` snippet has none in a turn you start in Desktop, the terminal UI or an editor over ACP, where you can stop it; elsewhere (`haarness run`, schedules, Cloud, scripts) it keeps this deadline. The former 600000 ms maximum is removed. |
| `subagent_concurrency` | 4 | Running child agents per delegation depth. Must be positive. |
| `subagent_depth` | 1 | Root → child by default; `2` enables grandchildren; `0` disables task delegation. |
| `read_parallelism` | 8 | Consecutive native observations run together up to this count. Must be positive. |
| `media_max_bytes` | 20971520 | Inline media read limit, now 20 MiB. Must be positive. Client attachments and common provider adapters use a 20 MiB aggregate cap; Gemini retains its 10 MiB aggregate adapter budget. Provider-specific transport limits still apply. |
| `code_timeout_ms` | 60000 | Code Mode deadline; `0` disables it. |
| `code_max_calls` | 100 | Code Mode tool-call budget; `0` disables it. |
| `code_max_source_bytes` | 262144 | Code Mode source size; `0` disables this check. |
| `plan_read_tools` | `[]` | Exact trusted `ext__…` tool names allowed in plan mode. Wildcards are rejected. |

Reads, listings, globbing, grep, web fetches and task delegations can run together: a batch of `task` calls launches its child agents side by side, bounded by `execution.subagent_concurrency`, and the TUI lists each child under the batch row with its own live status. Any other batch keeps its row and lists one line per step under it (while it runs, a spinner on the step the turn's status names, ● on the steps before it and ○ on those still to come; then ● or ✗; the tool and its target, matched to the result's entries ignoring case and namespace as the server resolves names), showing the first five of a longer batch and `… +N more` until the row is opened; because the server reports failed steps in the batch result's `failures` rather than failing the call, the TUI reads that count and marks the row `✗ batch  N failed`. Search rows name the pattern and the folder (`grep TODO in src`), as Desktop's do. Writes, shell commands and tools without an explicit parallel-read contract remain ordering barriers. Batch calls preserve those barriers and return results in input order. The Nth step runs as call `<batch call id>:N`, counting a step refused before it starts (an unknown or disallowed tool), so a client can pair a delegation's child with its step. Task agents have a separate pool at each depth so a parent waiting for a grandchild does not consume the grandchild's only slot. Cancellation still reaches descendants.

`write`, `edit`, `multiedit` and `apply_patch` hold each file they change, within the server process, from their first read until its formatter is done, so child agents or chats changing one file take turns instead of one undoing the other, and the editor's save, rename or delete of such a file (`PUT /v1/files/content`, `POST /v1/files/action`) waits for them too, without holding up changes to other files; a call waiting its turn still ends on Stop. A formatter a `PostToolUse` hook runs works after the file is released. A patch (`apply_patch`) is worked out in full before it writes: when a hunk does not match, no file changes and the error says so, and when a write fails partway (a folder in the way, a full disk) the error names the operations already applied. Each operation sees the files as the earlier ones leave them, by another letter case too in a folder that ignores case (each folder is asked, so a case-sensitive disk mounted inside one keeps `Foo.txt` and `foo.txt` apart), so deleting `README.md` and adding `readme.md` renames the file. A patch keeps every line's own line break, CRLF or LF, and the lines it adds take the break most of the file's lines use. A hunk closed by `*** End of File` matches only where it ends the file, and a hunk of only `+` lines adds them at the end of the file whatever its `@@` locator, as Codex does. An `@@` locator names the first line it equals (spaces around it aside); when the hunk is not found after that line, it is looked for after the first line that merely contains the locator, as before. A locator no line contains is passed over, as before too, so a hunk of only `+` lines under it is still added at the end, where Codex refuses the hunk.

Child agents started together share a prompt prefix. On a provider with explicit prompt caching (Anthropic and Claude through the Haarness Cloud router), the first child's request goes alone and its siblings' first requests follow once its response begins streaming (at most 20 seconds later), so they read the cache it wrote instead of writing the same prefix again. See [Dynamic workflows](WORKFLOWS.md#context-api) for the details; the same applies to workflow agents.

A child agent (a task, a workflow and its agents) is bounded by every chat above it. Each one's rules and ceiling are checked on their own, so a parent whose rules end with a broad allow never reopens another's deny: the plan agent started from a build chat still cannot write (`PermissionEngine::add_inherited_ceiling`). These inherited denials refuse calls but never take a tool out of the child's list. Sessions of one agent then send one tool list whichever chat started them, so they share one cached prompt prefix, which starts with the tools. A call to a tool a parent denies outright fails with "tool image_generate is denied by the rule 'media_generate:*' of the chat or agent that started this one, which no rule here can lift. …". The child's own agent rules and ceiling (the plan agent's, a custom agent's `permission`) still take tools out of its list.

A `bash` tool command runs without `CDPATH`, whether inherited, given by a `shell.env` hook or set by the login shell's profile, so `cd sub` goes to the folder the command and its approval card name (`crates/haarness-ripgrep/src/lib.rs`). Your own login profile can still send `cd` elsewhere, with a read-only `CDPATH` or a `cd` function, and the card cannot tell.

Shell output is streamed to a file with a bounded preview in memory. Large output exposes the full file path. Cancellation and deadlines terminate the shell process group on Unix; `0` removes the deadline, not the Stop control. A server that stops ends the commands it started; one killed or crashed cannot, so on Unix each running command's process group (and each workflow's, extension host's and MCP server's) is written beside the folder's server lock while it runs, and the next server for the folder, once it holds that lock and only when the server that wrote the record is gone, stops the groups still running as they were started: the same pid leads the group, with the same start time (read from `/proc` on Linux, from `ps` elsewhere), so a pid the system gave to another program is never stopped. A group whose leader already exited is left, and an entry the system cannot check is kept for the next server. A server that stops normally gives its record up before it releases the lock, so the processes it is still stopping are left to it. On Windows a command a crashed server started is not stopped. Stdout stays separate in metadata for dynamic definition context. This does not add a new background-shell job API.

A command the agent runs says it is an agent's, for scripts and tools that adapt to one: it gets `AGENT=1`, `HAARNESS=1`, `AI_AGENT=haarness` and `HAARNESS_SESSION_ID`, the id of the chat it runs in (a child agent's or a workflow's own chat for theirs), and no `OPENCODE_*` markers, which would name another product. This covers the model's `bash` calls, alone or as a `batch` step, in the foreground and in a background child agent, a workflow's `ctx.shell`, and the `` !`…` `` blocks of commands and skills, which the agent's turn runs; Code Mode's `execute` runs no shell commands. An `AI_AGENT` that is already set names an outer agent that runs Haarness, and is kept, unless it is `haarness`, Haarness's own. The others win over the server's own environment and over a `shell.env` hook or extension. A person's own `!` command in the TUI and a terminal are the person's: Haarness adds none of them there. The runtime tells the two apart by where a command comes from: the TUI's `!` reaches the server through `POST /v1/threads/{id}/shell`, a person's own direct call, while everything else runs inside the agent's turn or a workflow. A server that `haarness run`, the TUI or Desktop starts in the background leaves out Haarness's own markers its client was started with (`AGENT`, `HAARNESS`, `HAARNESS_SESSION_ID`, and `AI_AGENT` when it is `haarness`), as when an agent's command runs `haarness run` in another folder: the server outlives that command and serves a person's commands and terminals, and its own agent commands are marked again. A server that holds them all the same (a `haarness serve` an agent's command ran, which a person's TUI, Desktop or `haarness run` can use later) leaves them out of a person's `!` commands and terminals. An outer agent's own `AI_AGENT` stays, there too. A `HAARNESS_SESSION_ID` that the server itself inherited (a `haarness serve` an agent's command started) is left out by a person's `!` command, a terminal, a hook, an MCP server (and its `headersHelper`), an extension, a language server, a formatter, and the Git commands of reviews and worktrees (with the hooks Git runs), as they leave out the server's credentials and `OTEL_*` settings (see [Observability](OBSERVABILITY.md#data-handling)); an agent's command gets its own chat's. Each command the agent runs logs one `agent shell environment set` line (see [Observability](OBSERVABILITY.md#diagnostic-log-lines)).

## Secret files

The built-in `read` rules (`PermissionEngine::build_defaults`, `crates/haarness-core/src/permissions/mod.rs`) ask before reading `*.env` and `*.env.*` files, such as `.env`, `prod.env` and `.env.local`. `*.env.example` stays readable, and so does a file inside a `node_modules` folder at any depth (`node_modules/bottleneck/.env`, `packages/app/node_modules/pkg/.env.test`), because packages ship `.env` files as fixtures. `mynode_modules`, `node_modules.bak` and `node_modules_x` are other folders. Configured rules come after these, so a configured `read` rule for `*.env` still covers a file inside `node_modules`. The rules match absolute paths too, so in a project whose own folder is inside a `node_modules` folder, a read that names a `.env` by its absolute path does not ask; configure `"*.env": "ask"` and `"*.env.*": "ask"` under `read` to keep the ask there.

- **Either spelling of a project file.** A `read`, `edit` (also `write`, `apply_patch` and `multiedit`) or `list` rule names a file inside the project whether the call gives its path relative to the project or absolute (`PermissionEngine::set_workspace`). `"read": {"secrets/*": "deny"}` refuses `read /path/to/project/secrets/key`, and `"edit": {"/path/to/project/vendor/*": "deny"}` refuses `edit vendor/lib.rs`, in configured rules, inherited ceilings and remembered answers alike. A path through a folder link, such as macOS's `/var` for `/private/var`, counts as inside the project too, and `./secrets/key`, `src/../secrets/key` and `build/` are `secrets/key`, `secrets/key` and `build`. A patch (`apply_patch`) meets the `edit` rules for every file it adds, changes, deletes or moves to (`*** Move to:`), and for where each really leads. The active skill's own rules follow the same matching. A rule starting with `*`, such as the built-in secret rules, matches the path as written, and a path outside the project keeps matching rules as written. An `external_directory` ask names the folder a path really reaches, so a rule for an outside folder written through a folder link, such as `"external_directory": {"/tmp/*": "allow"}` on macOS (where `/tmp` is `/private/tmp`) or a folder under a linked home, also meets the ask for the folder the link leads to. Such a link is followed once per server process, when the rule is first loaded, and again only after a configuration reload, so a stale network folder holds up one check rather than every tool call and a link swapped later does not carry the rule along; an **Always** answer or a repository grant is never followed, since it already names the folder its ask named.
- **Where a file really is.** `read`, `edit`, `write`, `multiedit` and `list` also check the path the tool opens, after links and `..`, whenever it differs from the path the model gave (written workspace-relative when that was). A link `notes.txt -> .env` asks for `.env`, `node_modules/pkg/../../.env` asks like `.env`, and `list alias` for a link `alias -> build` meets `"list": {"build": "deny"}`. A rule that denies or asks for a link's target applies to the link. A workflow the agent creates (`workflow` with `action: create`) meets the `edit` rules for `.haarness/workflows/<name>.ts` and, when that folder is a link, for where the file really lands. An **Always** answer for such a read remembers both paths. A patch that deletes a file, or moves one away, removes the entry itself, as `rm` does: `*** Delete File: alias` for a link `alias -> real.txt` removes the link and leaves `real.txt`, and only the folder holding the link is checked, so deleting a link that leads outside the project asks nothing about the outside folder. A move still reads through the link, so the file it leads to meets the rules (and its folder is asked about when it is outside); the link is removed and that file stays.
- **A leading `~` is the home folder.** The file tools (`read`, `write`, `edit`, `multiedit`, `apply_patch`, `list`, `glob` and `grep` paths, `lsp`, `preview`, a shell call's `workdir`, a workflow `start` by `path`, a `skill_manage` or `plugin_manage` import, and the `file_path` a `FileChanged` hook is given) read `~` and `~/notes.txt` (and `~\notes.txt` on Windows) as a shell does, in the home folder (`HOME`, else `USERPROFILE`), so `write ~/Desktop/notes.md` asks `external_directory` for `~/Desktop` and writes there, never into a folder named `~` inside the project, and a rule written with `~` (`"read": {"~/.ssh/*": "deny"}`) meets the path written either way, as does the protection of [Haarness's own configuration files](#haarnesss-own-configuration-files) (`edit ~/.config/haarness/config.toml` asks). The tool's ask names the path once, as written, on the card and in the rule an answer suggests; `PermissionRequest` hooks and `permission.ask` extensions are asked about the file in the home folder (its absolute path, also as the tool's `path`), so a hook keyed on absolute paths meets it. `~name/…` and a `~` anywhere else (`notes/~/a`) stay as written; a project folder that is itself named `~` is written `./~` (`./~/draft.md`).
- **Hooks and extensions judge that file too.** A `PreToolUse` allow and a `permission.ask` or `PermissionRequest` answer about the path the model gave never settle an ask about the file it really opens. `PermissionRequest` hooks and `permission.ask` extensions are asked about that file in a call of its own, with the tool's `path` set to it (`tool_input.path` for hooks, `detail.path` for extensions) and the call's patterns naming it; the prompt is answered only when every call allows, and a deny in any refuses it. So a hook that allows reads unless the path ends in `.env` allows `notes.txt` but not the `.env` it leads to, and the person is asked. The same holds for a file path inside the project that a link takes outside it: the `external_directory` ask names the folder the file is really in, and hooks see that file's path. A direct tool call (a workflow's `ctx.tool()`, `!` shell) runs `PreToolUse` hooks but no `PermissionRequest` hooks, as before.
- **Search tools.** `grep`, `glob` and `list` never ask about secrets; they leave out every file these built-in rules ask about and end their output with the count, such as `(skipped 2 files with a secret's name)`, also given as `skipped` in the result metadata. A file is checked by its own path, by the path the model named (a search path may run through a link), and, for a link, by where it leads, so a linked workspace package under `node_modules` does not hand out its `.env`. `grep` checks a file or link given as its path before reading it, and returns `No files found` with the note. Its tree walk skips hidden files and folders (including a `.env` virtualenv) and does not follow links, so those are neither searched nor counted. When `glob` stops at its 10,000-result limit, or `grep` at one of its limits, the note says `(skipped at least N secret-named files)`. `grep` searches at most 20,000 files and returns at most 10,000 matching lines; when there are more files or matching lines, it ends with `(stopped after searching 20000 files; narrow the pattern or the path)` or `(stopped at 10000 matching lines; narrow the pattern or the path)`; a matching line longer than 2000 characters shows its first 2000 (a line is searched in its first MiB), a file that is not UTF-8 throughout is not searched, and its walk runs off the server's async workers, so **Stop** ends the call at once. Folders stay listed; only files are left out. `glob` stays in the folder it searches: a pattern with a `..` part is refused (`a glob pattern cannot contain ..; pass the folder to search as path`, so an outside folder is asked about as for `list`), a part such as `.*` never matches `..`, and `**` leaves out what it finds in a linked folder that leads out of both the project and the searched folder, ending its output with the count so the model does not take those files for absent: `(skipped 3 matches inside links that lead outside the project)`, also given as `outside` in the result metadata. A link itself is still listed. A `**` follows a linked folder unless the link leads back into a folder the walk is inside (one that holds the link, such as `/` or the home folder, or one it came through), so a link loop ends instead of walking until **Stop**, and it does not go into version control folders (`.git`, `.hg`, `.svn`, `.bzr`, `.jj`, `_darcs`, `CVS`), though a pattern that names one still reads it. A glob looks at no more than 100,000 matches, those it leaves out included, and then ends with `(stopped after looking at 100000 matches; narrow the pattern or the path)`; as a safety net it reads at most 1,000,000 folder entries through links, ending with `(stopped after reading 1000000 folder entries through links; narrow the pattern or the path)`, while every folder reached without a link is read whatever its size. Its walk runs off the server's async workers, and **Stop** ends the call before the next folder it reads.
- **Files a read rule denies.** `grep` and `glob` also leave out every file a `read` rule denies for the agent searching (configured, the agent's own `permission`, or a chat above it), judged the same three ways, and count them apart: `(skipped 2 files a read rule denies)`, or `(skipped 1 file with a secret's name and 2 files a read rule denies)`, with `denied` in the metadata beside `skipped`. A workflow's own `grep` and `glob`, run outside a turn, leave them out by the same rules. So `"read": {"private/*": "deny"}` keeps `grep` from returning a line of `private/key.txt` and `glob` from naming it. `list` still names such files (it never reads them), and an `ask` rule hides nothing. A `Read(…)` in the `disallowed-tools` of a skill or command the turn runs leaves files out the same way for every `grep` and `glob` after it in that turn, and in the subagents it starts; a bare `Read` there hides every file from them. The skill or command's own `@` files are still attached.
- **Instruction imports.** An `@import` in `AGENTS.md` or another instruction file never reads a secret-named file or a file a configured `read` rule denies, judged by where it really leads; `[Instruction import omitted: <path> (…)]` takes its place in the prompt. See [configuration scopes](CONFIGURATION-SCOPES.md).
- **Not covered.** An explicit `read` of a secret-named file still asks, and in Auto the reviewer answers it like any other eligible request. A `bash` command such as `cat .env` is not checked against the `read` rules. The file search behind `@` completion and Desktop's explorer and search (`GET /v1/files/search`) serves people, not the model, and still lists such files; a file a person picks there is attached by their own choice.

## How rules read shell commands

A `bash` rule, such as `"bash": {"git push *": "ask"}`, meets each command in the line as written: `git add -A && git push` meets the rules as `git add -A` and as `git push`. Each command is also read the ways the shell runs it, and every reading meets the rules too (`crates/haarness-core/src/permissions/bash.rs`):

- **Other spellings.** Without its leading assignments, quotes, backslashes or the program's folder: `FOO=1 git push`, `"git" push`, `\git push` and `/usr/bin/git push` are also read as `git push`, and `git push "--force"` as `git push --force`.
- **Backslash lines.** A line that starts with a backslash (`\rm -rf build`, a way to skip an alias) is a command of its own, as the shell runs it: after a line that ends a command, an assignment or a comment, in a subshell, a group or a substitution, and as the first line of a here-document fed to a shell. So `true` followed by a line `\rm -rf x` meets an `rm *` rule, a remembered `npm run *` does not answer `npm run build` followed by such a line, and its paths outside the project ask. A line that is only a backslash joins the next line to it, which is a command of its own too. A backslash before a Windows line ending (`\` then CR LF) quotes the carriage return, so the line feed ends the command and the next line is a command of its own: `true \` CR LF `rm -rf x` meets an `rm *` rule, and a script edited on Windows reads as the shell runs it, its continuations as separate commands. A line continuation that touches a word is joined as the shell joins it: `r\` at the end of a line and `m -rf x` on the next is also read as `rm -rf x`, and `rm\` then ` -rf x`, or `git \` then `push --force`, as `rm -rf x` and `git push --force`, so rules meet them as written on one line. A continuation between blanks (`cargo test \` then `  -p x`) keeps its line break in the command as written, as extra spaces do, so a rule of several words such as `git push --force*` meets `git push \` then `  --force` only through a rule on fewer words (`git push *`). Other backslash forms are read as before, and so is text in quotes or in a here-document, and a line of a here-document's text that starts with that document's delimiter once its backslash is gone, blanks before it or not, since the parser ends a document at such a line (only the here-documents the parser finds count, each for its own text: a `<<` in a string, a comment or `$((1<<2))` opens none, and `<<r` later in the line leaves a `\rm` line before it alone). Reading these shapes costs one more parse of the line and a pass over it, however many of them it holds.
- **Words after a redirect.** A command's words written after a redirect or a here-document operator are its own (`rm 2>&1 -rf ~/x` is `rm -rf ~/x`), for rules and for the outside-the-project check.
- **Lines the parser trips on.** The parser rejects some lines the shell runs, such as a redirect after a here-document followed by a pipe (`python3 - <<'EOF' 2>&1 | tail -20`) or two here-documents on one line. They are read as before, and what follows such a pipe or operator to the end of its line is read as a command line of its own, at the top level, so `tail` meets a `tail *` rule and `… | rm -rf x` an `rm *` deny. A here-document the parser could not attach to a shell that runs it leaves that one command not read whole, so a narrower deny or ask for what it might run applies.
- **Wrappers.** The command after the options of `sudo`, `doas`, `env` (and its `NAME=value` words), `command` (not `command -v`), `builtin`, `exec`, `nohup`, `setsid`, `nice`, `ionice`, `chrt` and `taskset` (after the priority or mask), `flock` (after the lock file, or its `-c` text), `timeout` and `gtimeout` (after the duration), `time`, `stdbuf`, `caffeinate`, `busybox`, `pkexec` and `xargs`, and each `find -exec`, `-execdir`, `-ok` or `-okdir` up to its `;` or `+`. So `sudo -u root rm x`, `timeout 5 rm x`, `xargs rm` and `find . -exec rm {} +` are also read as `rm`. Wrappers stack: `sudo FOO=1 timeout 5 nice rm x`.
- **Text a shell runs again.** The word that `bash`, `sh`, `zsh`, `dash`, `ksh`, `fish` and other shells run under `-c` or a flag cluster holding `c` (`-lc`, `-xc`, `-ec`, `-cx`; `-o name` is skipped), fish's `--command`, `su -c`, the words `eval` joins (`$'…'` decoded), `env -S` and `--split-string`, a here-document or here-string fed to a shell or to `source /dev/stdin` (or `.`), also where it is written after a list, a `!`, a subshell or a group, or a pipe (`false && bash <<'EOF'`, `(bash) <<EOF`, `echo ok | bash <<EOF`, where the document, not the pipe, is the script), what `echo`, `printf` or `cat <<EOF` pipes into one, and a shell or `source` of `<(echo …)`. That text is read as a command line of its own, at most four levels deep (`bash -c "eval 'sh -c …'"`), each text once for the command it comes from.
- **Backquotes in a here-document.** The shell runs the commands in backquotes inside a here-document whose delimiter is not quoted while it writes the document, so `cat > notes.md <<EOF` holding `` `npm test` `` (or a Markdown code fence) runs `npm test`. They are read as text a shell runs again: an `rm *` deny refuses `` `rm -rf build` `` there, while a rule that covers the command as written (`"cat *": "allow"`, a blanket `*`) adds no question for them, as for `bash -c`. This covers a document of a loop, a group or an `if` (`while read -r l; do …; done <<EOF`), read for the command written last before its `<<`, and backquotes in a `${…}` there (`${X:-`…`}`). `` \` `` is a backquote, a backquote never closed runs nothing, `$(…)` there is read as before, and `<<'EOF'`, `<<"EOF"` and `<<\EOF` keep their text as text. Past the limits below, the command is one a limit stopped reading. A document no written command opens is not read, and the command written nearest to it in the line, or the line itself, counts as one a limit stopped reading: `X=1 <<EOF`, `> out.txt <<EOF`, and one a `cd` opens (`cd src <<EOF`, `{ cd src; } <<EOF`, a loop that ends in `cd`). A line that starts with `<<EOF` is read by the parser as commands, its backquotes included.
- **Limits.** Reading stops at 16 wrappers, strings and `cat` stages deep together, a text longer than 256 KiB, 1 MiB of text read again in one line, 4,096 commands read inside such text (an ordinary script fed to `sh` is read whole), 64 readings of one command's own spellings and wrappers, or 4 MiB of patterns in the line (past it, and for a line over 1 MiB, the line is unreadable: readings stop, its commands are kept with their patterns clipped, and their paths outside the project still ask), so a thousand stacked wrappers, a long pipe of `cat` stages or a long here-document costs little.
- **A command a limit stopped reading.** Its readings may have missed what a rule is about, so a `bash` deny that does not cover the command as written, in any layer (a parent agent's limits, the configured rules, an active skill's), refuses it, with a reason that names the rule and asks to split the command. Otherwise such an ask makes it a question only a person answers, every time, as an edit of Haarness's configuration is: no **Always**, and not Auto, `--yolo`, a hook or a run nobody watches (a schedule refuses it at once). The card says "Haarness could not read all of this command; a rule for … may apply." Without such a rule it runs as before. An unreadable line goes further, since nothing is known of what it runs: no allow rule, remembered answer or **Always** settles it, even one for its first command (`"echo *": "allow"` does not open `echo $(echo $( … )); rm -rf ~/x`). Any `bash` deny refuses it, and otherwise only a person answers it, every time; the card says "Haarness could not read all of this command." when no rule is named.

**What a reading changes.** A reading only adds verdicts, and only from a rule about it: a deny or ask whose pattern does not also cover the command as written. It is judged in every layer (a parent agent's limits on a child, the configured rules, remembered answers), each passing over the rules that also name the command as written, and a deny or ask about it counts wherever it stands in the list, also before a blanket rule. So `"rm *": "deny"` refuses `bash -c 'rm -rf build'`, `sh -xc 'rm x'`, `eval "rm x"`, `env -S 'rm x'`, `xargs rm`, `find . -exec rm {} +`, `sudo rm x`, `nohup rm x`, `timeout 5 rm x`, `command rm x`, `/bin/rm x` and `\rm x`, and `"git push *": "ask"` asks for `FOO=1 git push`. A rule that covers the command as written has judged it already: under `"bash": "ask"` with `"timeout *": "allow"`, `timeout 5 cargo test` runs without a question as before, and `FOO=1 git status` asks once, as before, not again for its reading. A command with nothing to read gets exactly the verdict it got before, also in Auto and in runs nobody watches. An allow never reaches a command through a reading: `"git *": "allow"` does not open `FOO=1 git status` under `"bash": "ask"`, since an assignment such as `GIT_SSH_COMMAND=…` changes what git does, and `./git` is not git. A command written on its own in the line (`rm x; sudo rm x`) is judged as written. A child agent whose parent allows only `timeout *` (with `*` denied) can run `timeout 5 cargo test`, and its own `"tool-x *": "deny"` still refuses `timeout 5 tool-x a`. A rule that names both the command as written and its reading, such as `"*tool-x*": "deny"`, is passed over for the reading: followed by `"sudo *": "allow"`, it leaves `sudo tool-x a` allowed, as the rules' order says for the command as written. A reading can also be stricter than the command itself: with `"tool-x *": "deny"` followed by `"*": "allow"`, `tool-x a` runs (the later allow wins for it), while `sudo tool-x a` is refused (its reading meets the deny, and the blanket allow is passed over). The approval card shows the whole command, and the request is named after the command as written (in logs and in the refusal a scheduled run gets), while its patterns name the readings a rule asked about. **Always** remembers the generalized rules of exactly what was asked: `tool-x *` when only the `tool-x a` in `sudo tool-x a` asked, not `sudo *`. Under `"bash": "ask"` the written `sudo tool-x a` asks too, so an Always there remembers `sudo *` as well, as it always has for a command that asks.

**Not seen.** What a script file runs (`bash build.sh`, `source ./env.sh`; the card shows the file, see [The script a command runs](#the-script-a-command-runs)); text made at run time (`bash -c "$CMD"`, `eval "$(cat script)"`, `$(cat script)` as the program, a pipe from anything but `echo`, `printf` or `cat` of a here-document); an alias defined earlier in the line (`alias x='rm -rf'; x build`), and a shell function's arguments (`f() { rm -rf "$1"; }; f build`: its body is read as written, with `$1` as it stands); wrappers not listed above (`watch`, `flock`, `chroot`, `strace`, `ssh host cmd`, `npx`) and interpreters' own code (`python -c`, `node -e`); options a wrapper reads differently from the way described here; text past the limits above; and a `cd` inside the text (`bash -c 'cd /etc && rm x'` judges `x` from the project folder). Nor, of the backslash and here-document shapes above, any but those listed: another backslash form (`\$x` as a command name), a here-document line that starts with its own delimiter (`bash <<rm` holding a `\rm …` line), a line of an outer here-document before one nested in it, and a rule of several words against extra spaces or a continuation between blanks (`git push  --force` and `git push \` then `  --force` against `git push --force*`; a rule on fewer words, `git push *`, meets them). These readings are best-effort, not a guarantee. Like the check below, this guards against slips; it is not a sandbox.

## The script a command runs

Approving `bash /tmp/x.sh` approves what `x.sh` says, so every card a shell command raises also carries the script the command runs, read when it asks (`crates/haarness-core/src/permissions/script.rs`), for the card to show: a `bash` request under `"bash": "ask"`, and under the default rules, where `bash` runs without asking, the `external_directory` card of `cd /elsewhere && ./run.sh`. It is display only: it adds no permission, changes no pattern, and **Always** remembers the command's rules as before (so a script changed later runs under them without a question). What it promises is the faithful, current text of the file the command hands to its interpreter, or of the file it runs. It does not follow what that file loads in turn: imports, modules, files named in an interpreter's options. Rules, hooks, extensions and Auto never see it.

- **When it is read.** Only for a request a person sees. In Auto it is read when the request goes to a person (the reviewer asked, could not decide or paused, or Auto went off meanwhile; an ask a person configured; a request only a person answers), not before the review, so an approval without a card reads nothing; a card shown when Auto turns on keeps the script it was shown with. Each card reads it once, and is listed with it from the first: a card that waited on a review is listed only once its script is read. The file is read off the server's async workers with no approval lock held (before the lock is taken, or in Auto after the review, once the lock is released) and given 300 ms; a slower disk (a hung network or FUSE mount) shows no script rather than hold up the prompt.
- **Checked again.** The person may answer minutes later. When they allow exactly this request (**Allow once**, or any allow of a request that offers nothing longer), the file is read again, with 2 seconds to do it: if it changed, is gone, now leads elsewhere through a link, or cannot be read in time, the command does not run and the model is told "The command did not run: x.sh is not what it was when approval was asked (changed, moved or unreadable). Run it again to ask with the file as it is now." (Neutral, since who answered may not have read it: `haarness run` at a terminal, or Allow once, then Auto.) After **Always** (or another answer's **Always** that covers it, or Auto turned on while it waits) it is not read again: the remembered rule would let the retry through without a card anyway. A request that showed no script is not read again.
- **What counts.** A script is the file an interpreter runs after the options that take no value (`bash`, `sh` and the other POSIX shells; `python`, `python3`, `python3.12`; `node`; `perl`; `ruby`), a file `source` or `.` reads by a literal path with a slash, or a program run by its path (`./x.sh`, `/tmp/x.sh`). It is named when a step at the line's top level runs it, directly or through `sudo`, `env`, `timeout`, `nohup`, `command` or `exec`, from the folder the line's `cd`s lead to. Its own path's `..` is taken where the folder before it really is, as the system opens it: `sh lnk/../run.sh` names the `run.sh` beside the folder `lnk` leads to. A relative script is not named where the folder is not known for sure: after a `cd` that is not plain (below), a `cd` followed by `;` or a line break (it may have failed, and the next step runs anyway), `pushd` (which `dash` lacks), or a step that may redefine `cd`. Nor is one a wrapper runs in another folder (`env -C`, `sudo -D`, `sudo -i`), one under `/proc` or `/dev` or reached through a link into them (there the server's process answers, not the shell's: `/proc/self/cwd` is the server's folder, `/dev/fd/3` a file the server has open), nor any in a line the shell parser cannot read whole. Of several, the first that reads as text is shown, of the first four. On Windows, whose `cmd` reads a line differently (quotes, `^`, `%CD%`, `\`, drives), no script is named and cards are as they were.
- **Shown only in the shape people run.** Its text is shown when the script runs in the line's first statement, after nothing but plain `cd`s and `chmod`s joined by `&&`. A plain `cd` names one literal folder, with no leading `-`, no `$`, `` ` ``, `*`, `?`, `[` or `{`, no `~user` (a leading `~` is the home folder) and no `..`, which the shell takes off the folder's name while the file is read through its links. A plain `chmod` gives a literal mode and such paths. The script's own command has only literal words and no assignment before it, sends output only to literal files or descriptors, and goes through `sudo`, `nohup`, `timeout <duration>`, `command` or `exec` without options, if any. Started with `&`, it shows only when nothing but `wait` follows it. So `./run.sh`, `bash run.sh a b`, `cd d && chmod +x run.sh && ./run.sh > log 2>&1` and `nohup ./run.sh &` show it. A sourced file shows too (`source .venv/bin/activate`), and everything after it is withheld, since it can change the folder, `PATH` or anything else.
- **Withheld otherwise.** Anything else (`export X=1 && ./run.sh`, `set -e; ./run.sh`, `env X=1 ./run.sh`, `sudo -u bob ./run.sh`, another program, a test, a pipeline, a substitution, a here-document, a step after `;` or a job started with `&`) names the script with one quiet line instead of the text: "An earlier step of this command can change x.sh, so its contents aren't shown.", or, when the line plainly writes it first (a redirect, `tee`, `cp`, `mv`, `install`, `ln`, `curl -o` or `wget -O` naming it or a folder holding it, or its own output sent to it, also through a link), "This command writes x.sh before running it, so its contents can't be shown." Output sent into `/proc`, or through a link into `/proc` or `/dev`, gives the first line. Nothing is read then, and nothing is checked again. Changes made outside the line (`git pull` in another terminal, another process) show the file as it was when asked; an Allow once is checked against that just before the command runs, not while it runs.
- **What is shown.** At most the first 30,000 bytes (the card then says "Only the start of the file is shown."), with line breaks as `\n` and other control characters (tabs aside), bidirectional controls and marks, and Unicode line and paragraph separators as `�`, so a script cannot hide a line from the person reading it; its path gets the same, line breaks and tabs included. ACP clients get the path in a code span its own backticks cannot close. The size the card gives a cut file counts only what was read ("first 812 lines"). An empty file, a binary (a NUL byte), a folder, a device or pipe, and a missing file show nothing. Run by its path, a script runs through the program its `#!` line names, with that line's own words first (`#!/bin/sh /x/evil.sh` runs `evil.sh`), so its text shows only for these shapes: no `#!` line; `#!` and the rooted path of `sh`, `bash`, `zsh`, `dash` or `ksh` with nothing more than `-e`, `-u` and `-x` options (`#!/bin/bash -eux`); `#!` and the rooted path of `python`, `python3`, `python3.N`, `node`, `perl` or `ruby` alone; or `#!/usr/bin/env` and one of those names alone (`#!/usr/bin/env python3`). Any other `#!` line shows nothing, `#!/usr/bin/env -S …` and `#!/bin/bash -euo pipefail` included, and so does one whose interpreter is under `/proc` or `/dev` or is a script itself. `perl` runs the program its first line names with `#!` (found as perl finds it, also after white space, a `:` or a byte order mark) when that line does not say `perl`, so such a line shows nothing under `perl` (`perl x.pl` with `#!/bin/sh evil.sh` runs `evil.sh`). `bash`, `sh`, `python` and the other interpreters read the line as a comment, also run by their own path (`/bin/bash run.sh`). Nor does a file that declares, on one of its first two lines, a source encoding that can turn bytes into other text (`# coding: utf-7`, `unicode_escape`, UTF-16 or UTF-32, `shift_jis` and the other multi-byte ones): Python reads it by that encoding, and could run a line the card cannot show. UTF-8, ASCII and the single-byte ISO 8859 and Windows code pages (`latin1`, `iso-8859-15`, `cp1252`), by any of Python's names for them, show.
- **What is never shown.** Only what the chat may read is shown: its `read` rules (the [built-in secret rules](#secret-files), configured rules, an agent's own, a parent chat's limits and remembered answers) must allow both the file named and where it leads, and an active skill's `disallowed-tools` must not deny reading it, so `"read": {"secrets/*": "deny"}` or `"ask"` keeps `bash secrets/run.sh` off the card. A file outside the project is shown when its folder's `external_directory` rule asks (that is often the very question the card asks), not when it denies. Files that hold or export credentials never show, whatever the rules say: private keys (`id_rsa*`, `id_dsa*`, `id_ecdsa*`, `id_ed25519*`, `*.pem`, `*.key`, `*.p12`, `*.pfx`), `.aws/credentials`, `.netrc`, `.git-credentials`, `.npmrc`, `.pypirc`, `.envrc`, and shell rc and profile files (`.bashrc`, `.bash_profile`, `.bash_login`, `.profile`, `.zshrc`, `.zshenv`, `.zprofile`, `.zlogin`), judged on the name and on where a link leads. Agents source these often (`source ~/.zshrc`), and the card would otherwise show their keys.
- **Clients.** The request (`GET /v1/permissions` and the `permission.requested` event) has an optional `script { path, content, truncated, withheld }` (`withheld` is `written` or `changeable` when the text is not shown; a client reads a reason it does not know like `changeable`); an older server sends none, and the card stays as it was. It reaches everyone who can see the request: every client of the server (the terminal UI, Desktop, ACP clients, SDK and `/v1/events` subscribers, and the server's replay of recent events), and the viewers of a chat shared through remote control or the Cloud relay. Desktop shows a quiet **View script · N lines** toggle under the command, closed by default so the card keeps its size; opened (by click, or Tab and Enter), it shows the path and the text in the change style, long lines wrapped whole, in a short box that scrolls on its own. The terminal UI shows the script's name and size and its first lines under the command, behind a gutter, long lines wrapped whole; ↑↓ scroll it and ctrl+e expands the card to read it whole, as for a long command. ACP clients get it as the request's tool call content (Markdown). `haarness run` at a terminal prints its path and first six lines above "Allow it once? [y/N]", each cut at 200 terminal columns with `…`, or its quiet line when the text is withheld. The script is not kept in the chat's history.

## Shell commands outside the project

`bash` runs without asking under the default rules, but a command that reaches outside the project asks `external_directory` for the folder it reaches (`crates/haarness-core/src/permissions/bash.rs`). The check reads the arguments of `cd`, `pushd`, `rm`, `cp`, `mv`, `mkdir`, `touch`, `chmod`, `chown` and `cat` (by name wherever the program lives, so `/bin/rm` counts), and every redirect target, resolved as the shell would: from the folder the call's `workdir` names (the project folder without one), or from where a `cd` earlier in the line took the shell (see **After a `cd`** below):

- **Devices.** A redirect to a device read or written as a stream asks nothing: `/dev/null`, `/dev/zero`, `/dev/full`, `/dev/random`, `/dev/urandom`, `/dev/tty`, `/dev/stdin`, `/dev/stdout`, `/dev/stderr`, a descriptor such as `/dev/fd/3`, and bash's network paths `/dev/tcp/…` and `/dev/udp/…`. Any other path under `/dev` is checked like any path: on Linux `/dev/shm` and `/dev/mqueue` hold files anyone can write, and a link there can lead anywhere, so `echo x > /dev/shm/x` asks for `/dev/shm`. A terminal device other than `/dev/tty` (`/dev/ttys001`, `/dev/pts/3`) is such a path too and asks.
- **New paths.** A path that does not exist yet is judged where it would be created, so `touch /tmp/new`, `mkdir -p /tmp/a/b`, `cp notes.txt /tmp/new` and `echo x > /tmp/new` ask like an existing file there. `..` inside the part that does not exist is taken the way `mkdir -p` creates it.
- **Links.** Links are followed, dangling ones too (writing through one creates its target), and `..` after a link goes up from where the link leads. A link chain the check cannot finish counts as outside (`/*`). The shell's own `cd` steps out of the path as written instead (`cd -L`, its default), so a `cd` is judged both ways and asks when either is outside: with `a/l` leading deeper into the project, `cd a/l/../../..` reaches the project's parent and asks, though followed it is the project itself. `cd -P`, which follows links, is judged both ways all the same, so `cd -P a/l/../../..` asks too. `pushd` enters a folder as `cd` does and is judged the same way (`pushd /etc && cat passwd` asks for `/etc`). A place in its folder stack (`pushd +1`, `pushd -0`) only returns to a folder the stack already holds, so it names no folder and asks nothing.
- **Home.** An unquoted leading `~` is the home folder, and `~name` that user's home (taken next to yours); quoted, `~` is just a name in the project. A leading `$HOME` or `${HOME}`, bare or in double quotes, is the home folder too, and so are `$TMPDIR`, `$HAARNESS_HOME`, `$XDG_CONFIG_HOME`, `$XDG_DATA_HOME` and `$XDG_STATE_HOME` when the server has them set to an absolute folder: `cp x.json $HOME/.config/haarness/haarness.json`, `echo x > "${HOME}/.profile"` and `cd $HOME` ask like their `~` spellings. In single quotes they are names. A `cd` given no folder (`cd`, `cd --`, `cd -P`) goes to the home folder, so `cd && rm -rf Documents` asks like `cd ~`.
- **Dynamic parts.** A value such as `/tmp/$name` or `~/$(date)` is judged by the folder its literal start names; one that starts with another variable, an expansion with an operator (`${HOME:-/x}`) or a substitution, such as `$OUT/x`, is not checked.
- **After a `cd`.** In a line that is one chain of steps joined by `&&`, a step's paths and redirects are read from where the `cd`s that open the chain left the shell, so `cd src && cat ../README.md` and `cd sub && echo x > ../out.txt` stay in the project and ask nothing, while `cd sub && cat ../../x` asks for the folder it reaches. A link in the folder is entered where it leads, as the system does. The `cd` itself is still checked from where the shell was, and so is a redirect on it, which the shell opens before it moves. A `cd` or `pushd` is followed only when it names one literal folder that is there when the line is checked: no `..`, no `$`, `` ` ``, `*`, `?`, `[`, `{` or `\`, no leading `-`, no `~user` (a leading `~` is the home folder), and not a place in the folder stack (`pushd +1`). Only the `cd`s at the start of the chain are followed: after any other step a `cd` is not, since that step may have set `CDPATH` or `HOME`, or made a link where the `cd` goes. The steps after them are read from their folder while each step before is a command that cannot move the shell: one whose program is written out (not `$run`) and is not `popd`, `eval`, `source`, `.`, `builtin`, `command`, `alias`, `time`, `trap`, `mapfile`, `readarray` or `enable`. Everywhere else paths are read from where the shell started, as before: after `;` or in a statement of its own, in a subshell (`(cd sub) && cat ../x`), a pipeline or an `||` list, after a `cd` whose folder is only known when it runs (`cd "$D"`) or is not there yet, and in what a step runs through a wrapper or a substitution.
- **Wrapped and nested commands.** The readings in [How rules read shell commands](#how-rules-read-shell-commands) are checked too: `sudo rm -rf /etc/x`, `timeout 5 cat /etc/hosts`, `bash -c 'touch /tmp/x'`, `eval touch /tmp/x`, `find . -exec cp {} /tmp/ \;` and a here-document fed to `sh` that writes to `/tmp` ask for the folder they reach.
- **Not covered.** Other programs' arguments are not read (`tee /tmp/x`, `sed -i … /etc/x`, `python -c …`). This guards against slips; it is not a sandbox.

## A chat's own folder

A chat created with a folder of its own (`directory` when it is created; in the [chat home](REFERENCE.md#the-chat-home) every chat has one) works in that folder, not in the server's project folder. Every such folder is `<project>/<date>/<name>`: two real folders, never a link, so no chat's folder is inside another's. For its tools the folder is both the working folder and the project (`ToolContext.workspace`, set per call by the runtime):

- **Where things run.** `bash` (the model's, a person's `!` and a workflow's `ctx.shell()`), file, search, LSP, workflow and preview tools resolve relative paths there, a `workdir` defaults to it, relative attachments are read from it, the system prompt names it as the working directory, and the plan agent's `.haarness/plans/` and a created workflow's `.haarness/workflows/` are inside it. A workflow created there is listed for that chat and can be started from it by name or path (its folder's `.haarness/workflows` is the chat's own, found whatever the project configuration setting); without project configuration, as in the chat home, it is trusted as inline source is: a portable workflow runs, a native one is refused. Language servers and formatters run in the folder itself (one language server per server and folder), and a language server's answers leave out places in other chats' folders (places outside the project, such as the standard library or a dependency cache, stay). The prompt calls it a Git repository only when the folder itself holds a `.git`, not when a folder above it does. [Hooks](CONFIGURATION-SCOPES.md#lifecycle-hooks) run there too, with the folder as their `cwd`; their `CLAUDE_PROJECT_DIR` (and its `HAARNESS_`/`OPENCODE_` spellings) stays the server's project folder, where its hook scripts are, except on the chat home, where it is the chat's folder. MCP servers still run in the server's project folder.
- **The boundary.** Everything outside the folder is outside the project, the server's own folder and other chats' folders included: the file tools (`read`, `write`, `edit`, `multiedit`, `apply_patch`, `list`, `glob`, `grep`, `lsp`, `preview`) refuse a path there without an `external_directory` approval, and ask for one. Path rules (`"edit": {"src/*": "deny"}`) name files relative to the chat's folder.
- **The shell is best-effort, exactly as for a project.** A `bash` command asks `external_directory` for another folder only where [Shell commands outside the project](#shell-commands-outside-the-project) reads it: the arguments of `cd`, `pushd`, `cat`, `rm`, `cp`, `mv`, `mkdir`, `touch`, `chmod` and `chown`, every redirect, and the same inside `sh -c`, `timeout` and the other readings, so `cat ../other/a.txt`, `echo x > ../other/x`, `cd .. && ls` and `rm -rf ../other/build` ask. Other programs' arguments are not read and run without asking: `ls ..`, `grep -r … ..`, `rg … ../other`, `find ..`, `git -C ..`, `stat`, `du`, `tar cf ../other/x.tar …`, `bash -c "ls .."`, `ln -s ../other link`, a path through `$PWD/..`, and any interpreter (`python3 -c …`). It guards against slips; it is not a sandbox.
- **Undo.** The folder is checkpointed by a store of its own, on by default even where the project folder is not (a plain folder, or the chat home), unless `snapshots.enabled` is `false`. Undo, Redo and the last turn's review then work in the chat and restore nothing outside its folder.
- **Ignore files.** In the chat home, `grep`, `@` file search and Undo's checkpoints read the ignore files of the chat's folder and the folders in it, never those of a folder above it. `.ignore` files always count. `.gitignore` files count for `grep` and Undo when a Git repository holds the chat's folder (a `.git` of its own or one above it, as in a home folder kept in Git), a repository's `.git/info/exclude` only when that repository is the chat's folder or a folder in it (a home folder's own never counts), and `@` file search reads `.gitignore` files either way. A `grep` of a subfolder finds what ripgrep finds there with the chat's folder as the outermost one (a `!` line, a repository nested in it and global excludes weighed as ripgrep weighs them), and a subfolder it names is searched even when an ignore file leaves it out, as ripgrep does. The chat home lives in the app's data folder, inside the home folder, so a home folder kept in Git whose `.gitignore` is `*` hides nothing from its chats, and a chat's `node_modules` stays out of `@` file search unless named, as in any folder outside Git. A project's folder still reads the ones above it, as Git and ripgrep do.
- **Schedules.** A schedule made in the chat runs in its folder. Such a chat sees, runs and changes only the schedules made in its own folder (another chat's read as not found), and cannot name a `workspace` for a new one. A chat without a folder of its own sees and acts on only schedules made without one.
- **Who shares it.** Task subagents, workflow chats and their agents, forks, and the runs of a schedule made in the chat work in its folder; a side chat answers with it in its prompt. A remembered answer (**Always**) still lasts for the whole server, as for any chat.
- **The folder itself.** The server makes it, one part at a time, never through a link, and refuses a folder that is not `<date>/<name>`, that would lead out, or that a link stands in for. The name is plain text: no control character, no space at either end, and no `-` or `.` to start it (so no `.git`, `.haarness` or hidden folder). Work that writes there (a turn, a person's or a workflow's tool call, Undo) makes a folder a person deleted again, empty; work that only reads (a review, a side question, an attachment, a mention, a list of the chat's workflows) never makes a deleted folder again. In the chat home, a chat stored before chats had folders gets one the first time it is used, by either kind of work (its parent's, when that has one). A chat whose folder was replaced by a link, or whose date folder was, is refused its turns and tool calls with a plain message until the folder is a folder again. A link swapped in while a command already runs is not caught, as for a project's own folder.

## Haarness's own configuration files

An agent that rewrites the files Haarness takes permissions, hooks, MCP servers and providers from could widen its own permissions at the next reload: a project whose rules ask before `bash` would stop asking once the agent added `"bash": "allow"` to its `haarness.json`. So `edit`, `write`, `multiedit` and `apply_patch` ask a person before changing `haarness.json` or `haarness.jsonc`, `opencode.json` or `opencode.jsonc`, `.haarness/config.toml` (and `.haarness/cloud/haarness.json`), `.haarness/extensions.json` and any file under `.haarness/extensions/` (extension code, which can answer approvals), `.claude/settings.json`, `.claude/settings.local.json`, `.mcp.json`, a plugin's `hooks/hooks.json` and `.claude-plugin/plugin.json` (a project's own plugins under `.haarness/plugins/` load as trusted), the global configuration folder's `config.toml`, `extensions.json`, `extensions/` and `prompts/` (the [prompt files](PROMPT-FILES.md) that are the agent's own instructions), also where they really are when the folder or a file in it is a link (dotfiles linked in with `stow`) (the folder this server really reads: `<data dir>/config` with `--data-dir` or `HAARNESS_DATA_DIR`, else `$HAARNESS_HOME/config`, else `$XDG_CONFIG_HOME/haarness`, else `.config/haarness` in the home folder), and every file of the [system folder](CONFIGURATION-SCOPES.md#system-folder) (`HAARNESS_SYSTEM_CONFIG_DIR`), as written or where it really is. They are matched at any depth, case-insensitively, without the trailing dots and spaces Windows drops (so `haarness.json ` and `.mcp.json.` count), and after `.`, `..` and links (a link `notes.json -> haarness.json` asks too) (`is_config_path` in `crates/haarness-core/src/permissions/mod.rs`). Reading them is unchanged.

- **Only a person answers.** The request offers **Allow once** and **Reject**, never **Always**, and nothing answers it in a person's place: not Auto, not a turn that approves its own requests (`haarness run --yolo`, a `--yolo` terminal UI, ACP), not `serve --yolo`, not a `PreToolUse` or `PermissionRequest` hook. A scheduled run, which cannot ask, refuses it at once ("'edit:haarness.json' needs the user's approval every time, and this scheduled run cannot ask …") and goes on, as it does for Cloud actions. `haarness run` without a terminal stops on it.
- **Rules that open it.** An allow rule whose last path segment holds the file's name, such as `"edit": {"haarness.json": "allow"}`, `"**/haarness.json": "allow"` or `"*.mcp.json": "allow"`, lets the edit run without asking, even when a blanket allow comes after it. Other allows never do: `"edit": "allow"`, `"*": "allow"`, `"**/*"`, a folder (`".claude/**"`, `".haarness/**"`), a kind of file (`"*.json"`) and an **Always** answer to another edit (which remembers `edit:*`) leave it asking. A deny refuses it as usual, and the plan agent still cannot write it.
- **Not covered.** A `bash` command that writes one of these files (`echo … > haarness.json`, `sed -i`) is not checked: the shell analysis cannot see every write, so this guards the file tools, not the shell. A command outside the project, such as one that writes `~/.config/haarness/haarness.json`, still asks for that folder (see [Shell commands outside the project](#shell-commands-outside-the-project)). The management tools (`mcp_manage`, `agent_manage` and the others) change configuration under their own permissions. A plugin's `mcpServers` may also name other JSON files inside the plugin; only `plugin.json` and `.mcp.json` are covered. A patch is checked by every path it touches, each `*** Move to:` destination included, so adding a scratch file and moving it onto `haarness.json` asks. A `*** Move to:` that names the file being updated (the same path, a `./` spelling, or another case on a case-insensitive disk) is refused before the patch writes anything, since it would write the file and then delete it.
- **Agent, command and skill definitions are not covered.** They follow the ordinary edit rules. An agent allowed to edit can write an agent, command or skill whose frontmatter declares permissions (`permission`, `tools`, `allowed-tools`, `disallowed-tools`, a command's `agent`, an agent's `mode: subagent`) and then use it: delegate to that agent, or invoke that skill or command. Options under consideration: a path-based ask for definition folders (`agents/`, `commands/`, `skills/`), a content-based check with patches applied atomically, or ignoring permission fields in definitions written during the session.

## Where Haarness keeps sign-ins

Haarness keeps the person's sign-ins in files of its own: provider keys and tokens in `auth.json` in the data folder (and the copy an older layout left in the configuration folder), MCP servers' sign-in tokens under `mcp-oauth/` beside it, the Haarness Cloud sign-in in `credentials.json` in its account folder, the servers the terminal UI saved with their tokens or passwords in `tui-servers.json` in the configuration folder, and each running server's address and token in `runtime.json` in the cache folder (one for each project, under `workspaces/`), which can answer that server's approvals, the ones only a person answers included. A model that reads one holds the keys to every provider the person signed in to, or to the server itself, and the read puts them in the transcript. So a model-run read or change of one asks a person every time, whatever the rules or earlier answers say (an **Always** for `~/*` included), and Haarness never puts one into a prompt itself (`is_credential_store_path` in `crates/haarness-core/src/permissions/mod.rs`, which the server records at start, and `instructions::left_out` in the same crate).

- **What counts.** Those files as this server keeps them, their temporary copies while they are saved (`auth.tmp-…`, `credentials.json.tmp-…`, `.tui-servers.json-…`, `runtime.tmp-…`), the `auth.json.lock` beside them, and every file under `mcp-oauth/`: by full path, after `.` and `..`, through a link in a folder or to the file, in any letter case. Never by name alone: a project's own `auth.json` is an ordinary file.
- **What asks.** A `read` of one, by any spelling or through a link; a change of one through `edit`, `write`, `multiedit` or `apply_patch`; and a `bash` command that names one as a literal path, as the argument of a program that may read or change it (`cat`, `head`, `jq . …`, `cp`, `chmod`), also as an option's value (`--files0-from=…`), or in a redirect (`< …/auth.json`). A program that only looks at the file whatever its options say (`ls`, `stat`, `test` and `[`, `readlink`, `realpath`, `basename`, `dirname`) decides as any command does; `file` and `du` are not among them, since `file -f`, `file -m` and `du --files0-from` read a file they are given. `grep`, `glob` and `list` leave them out and end with the count, such as `(skipped 1 file where Haarness keeps sign-ins)`, also given as `signIns` in the result metadata.
- **Never put into a prompt.** Haarness itself leaves one out of what it adds to a prompt, and says so where its text would be: an instruction file (`AGENTS.md`, also a link to one, or a file a project's `instructions` names) gives `[Instruction file omitted: … (Haarness keeps sign-ins there)]`, which the log also records (`config: skipped instructions …`), an `@` import in one `[Instruction import omitted: …]`, and an `@` reference in a skill or a command `[File context omitted: …]`. A command or agent file that is a link to one is skipped, and the log says so (`config: skipped command …`). A secret-named file (`.env`) and one a `read` rule denies are left out the same way (a template of settings that a skill or command names, such as `.env.sample`, `.env.template` or `.env.dist`, is read as before); for an instruction file the read rules count only when it is outside the project and not in the person's own folders, so a project's and a person's own instruction files load as before. A file a project's own `instructions` names outside the project is also left out, rule or no rule, when it holds credentials (`… (it holds credentials)`): anything in `~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.kube`, `~/.docker`, `~/.azure`, `~/.config/gcloud` or `~/.config/gh`, a `.netrc`, `.npmrc`, `.pypirc`, `.git-credentials` or `.pgpass`, a private key (`id_*` but not `.pub`) and key files (`.pem`, `.key`, `.p12`, `.pfx`, `.jks`, `.keystore`). The person's own configuration may still name them. A read rule written with `/var/…`, `/tmp/…` or `/etc/…` also meets a file whose real path is under macOS's `/private`.
- **Only a person answers,** as for [Haarness's own configuration files](#haarnesss-own-configuration-files): the request offers **Allow once** and **Reject**, never **Always**, and Auto, `--yolo`, `serve --yolo` and hooks never answer it. A scheduled run refuses it at once and goes on. A deny rule still refuses it.
- **Not covered.** A path the shell builds (`cat "$DIR/auth.json"`), a path relative to an earlier `cd` (`cd <data folder> && cat auth.json`), a read of the whole folder (`grep -r KEY <data folder>`, `cat <data folder>/*.json`), a program that opens the file by itself (a script, `python3 -c …`), and a copy kept elsewhere. So a project at the home folder, which holds the data folder, is protected only against naming the file. This keeps a model from reading the sign-ins by a slip or because a page or file told it to; it is not a sandbox.

## Web fetches

`webfetch` rules (`webfetch:<address>`) meet the address as written and, when it is written differently, the address the fetch really reads: scheme and host in lower case, without a user name or password, a trailing dot on the host, the default port, `.`/`..` path segments or a `#` fragment (the server never sees it), and with a `%` code in the path for a letter, a digit, `-`, `.`, `_` or `~` written as that character (a server reads `/%61dmin` as `/admin`; other codes, such as `%2F`, stay as written). An address with no path is also met as its `/` page, so a rule for `https://example.com/*` holds for `https://example.com#top`, and a host spelled in punycode also as its Unicode name, so a rule for `https://bücher.example/*` holds for `https://xn--bcher-kva.example/`. So a rule for `https://example.com/b/*` also applies to `HTTPS://user@Example.com.:443/a/../%62/x#top`; another port is another address. An allow for one page is best written in that plain form, since a spelling it does not match still asks.

A fetch follows redirects only while they stay on the host it asked for (the same host and port, or the same host moving from http to https), never from https back to plain http, and at most ten of them. Any other redirect (to another host, another port, or down to plain http after any step) is not followed: the result names the new address and why, and fetching it is the model's next call, checked against the rules like any other. Image and video generation follow their configured backend's redirects as before. A redirect within the host meets the `webfetch` rules as the address asked for does, in every form above, together with what an active skill's `disallowed-tools` denies, and is followed when they allow its new address. When a rule denies that address, the fetch stops there, and the result says a rule denies it, without asking the model to fetch it. When the rules ask about it, the fetch stops and returns the new address as above, with no new question. The one exception is a fetch asked about under a rule for the whole tool (`"webfetch": "ask"`): the answer it got was about no one page, so a redirect that rule asks about is followed as before. So a deny for `https://intra.example/admin/*` also holds when `/login?next=/admin/x` redirects there, and neither an **Allow once** for one page nor an allow rule for `https://intra.example/docs/*` leads to another page of the host. (An **Always** for a fetch is for the whole tool, `webfetch:*`.) A workflow's own fetch is judged the same way.

## MCP resources

When a connected MCP server declares resources, the model can list and read them with `mcp_resource_list` and `mcp_resource_read` (see [MCP resources](REFERENCE.md#plugins-skills-and-tools)). Like MCP tools, both run without asking unless a rule says otherwise. Rules use these names:

| Permission | Pattern it matches |
| --- | --- |
| `mcp_resource_list` | The server name. Listing every server asks about each server it lists, so a rule about one server still applies. |
| `mcp_resource_read` | `<server>:<uri>`. **Always** remembers `<server>:*`, every resource of that server and no other. |

Upstream OpenCode's names for the two tools, `opencode_list_mcp_resources` and `opencode_read_mcp_resource`, mean the same here, with the same patterns, so a rule in an `opencode.json` shared with OpenCode applies: `"opencode_read_mcp_resource": "deny"` refuses `mcp_resource_read` and takes it from the model. Such a rule takes its own place in the rule order, like any other.

In these patterns a server name keeps its letters, digits, `.`, `_` and `-`, and any other character is written `_`, so a rule `docs:*` never reaches a server named `docs:private`. A rule or setting that takes every tool of a server away (`"mcp__docs__*": "deny"`) keeps its resources from the model as well, before either permission is asked: a listing of every server leaves it out, and a read naming it is refused as configured policy. A resource a person picks from the `@` list in Desktop or the TUI is read without asking, as attaching a file is, and no `PreToolUse` hook runs for it, but a deny for `<server>:<uri>` under the agent the message runs under (or the running turn's agent, for a message sent while one works) still keeps it out of the message (see [MCP resources](REFERENCE.md#plugins-skills-and-tools)). To be asked before reading anything but one server's resources:

```json
{
  "permission": {
    "mcp_resource_read": { "*": "ask", "docs:*": "allow" }
  }
}
```

## Skills and plan mode

Dynamic `!` shell context in a skill or command now raises the ordinary permission prompt when it needs approval. A deny still prevents execution, and a nonzero context command still fails the invocation. Installed skill and enabled plugin helper directories receive read-only external-directory exemptions. Secret-file rules and canonical symlink checks still apply; these exemptions do not authorize writes or arbitrary home-directory access.

Plan mode permits browser tab inventory, frames, snapshots, find and screenshots. Browser evaluation, input, navigation and uploads retain their existing plan restriction. To allow an extension tool you have reviewed as observational, configure its exact name:

```json
{"execution":{"plan_read_tools":["ext__code_search__query"]}}
```

This is an operator assertion about that extension, not automatic analysis of JavaScript side effects. Explicit tool availability and permission denials still apply.

## Browser approvals

This section is about Desktop's Haarness browser; Chrome follows [Chrome approvals](#chrome-approvals). Settings → Browser offers **Remember site approvals**. It is off by default, preserving approval for every browser action on sites configured as **Requires approval**. Enable it to use ordinary session, folder or repository consent for each origin and capability (browsing, downloads, uploads). An existing site **Block** always remains effective. Every-time prompts offer Allow once and Deny in current clients.

Site rules accept exact origins and leading subdomain wildcards such as `https://*.example.com`. A wildcard includes nested subdomains, excludes the apex domain, and preserves scheme and port. Exact rules take priority, then the longest matching wildcard. `https://*.example.com` does not include `http://a.example.com`, another port, or `a.example.com.evil`. A host's trailing dot (`https://example.com./`, the fully qualified spelling) is the same site in rules and requests, so it neither escapes a Block nor needs a rule of its own; a rule saved with one is stored without it.

An upload needing file access and site consent shows one combined approval. Every underlying gate is evaluated before the prompt; a deny in any gate prevents the upload. Remembered rules retain their original permission categories.

An unapproved redirect or script request to another origin still stops at the site boundary. Navigate to that origin explicitly to authorize it, or configure a matching site rule. Pausing arbitrary Chromium requests for an additional in-flight approval is not introduced in this change; it needs a separate lifecycle implementation that handles navigation deadlines, cancellation and uncertain submissions without replay.

## Chrome approvals

An agent in the user's Chrome acts in the user's signed-in accounts, so a site that **Chrome site permissions** sets to **Requires approval** (the default for browsing, downloads, uploads and scripts) needs a person's answer, per chat and per origin. Only a person's answer counts, given in a client of this server other than a published chat; nothing configured in advance can give it, except a site the user sets to **Always allow** in the global Chrome settings, which no project can loosen (see [Chrome settings](BROWSER.md#chrome-settings)).

**Patterns.** For each HTTP(S) origin a Chrome command touches, the gate pushes the remember pattern `chrome-<category>:<thread id>:<origin>` (checked as the operation `browser_site:chrome-…`), with categories `browsing`, `downloads` and `uploads`, plus `scripts` for `browser_evaluate` even when browsing is already approved. Navigation and new tabs include the origin's `www.` twin. Because the pattern carries the thread id, a remembered answer never covers another chat. `BrowserTool::explicit_approval` returns true for operations starting `browser_site:chrome-`, and `RedefinedTool` in `crates/haarness-extensions` forwards it so a runtime extension that redefines a browser tool cannot drop it.

**What satisfies them.** `PendingPermission.explicit` is true when any asked pattern is explicit. An explicit pattern is satisfied only by an answered grant in the runtime's `session_rules` whose rule starts with `browser_site:chrome-` (`explicit_granted`). Configured rules (defaults, global and project configuration, Claude-compatible JSON, custom agents, `"*"`, `browser_site:*`) can only deny it.

**Bypasses that do not apply.** Explicit requests are treated like forced ones at every bypass: the direct-path and model-path hook skips, direct-path and model-path Auto, the release of waiting prompts when a chat switches to Auto, server `--yolo` (which also stores no session rule for them), a `PermissionRequest` hook's Allow, and the refresh fast path, which checks `explicit_granted`. Unlike forced requests they offer an "always" answer (`allowAlways: true`), store it, and may be released when an answered rule covers them.

**Answers.**

| Reply | Effect |
| --- | --- |
| `once` | This call |
| `always` | A session rule for this chat, origin and category, until the server stops |
| `always_workspace`, `always_repository` | Downgraded to `always`; never persisted |
| `reject` | The call fails, and so does every other request waiting in the conversation (a person's no) |
| `refuse` | For unattended runners only: the call fails, the conversation's other requests keep waiting, and the agent reads `feedback` as Haarness's reason rather than a person's answer. `haarness run` without a terminal stops on a Chrome request instead of refusing it |

Desktop's dock and the TUI card read `explicit` and show **Allow in Chrome** with humanised lines ("Use https://example.com in Chrome", "Send downloads from … in Chrome to the agent", "Upload files to … in Chrome", "Run scripts on … in Chrome"). Desktop offers **Deny**, **Allow once** and **Allow in this chat** (primary, `always`); the TUI uses `a` (Allow in this chat, a single press), `y` (once) and `n`, with no `w`, `r` or `u`. Both show the call's own arguments under those lines (the address, script, text or files), without `__browser`, so Allow once approves a call the person has seen. The popup of the Haarness for Chrome extension can answer the same request through the bridge, which forwards only explicit approvals waiting on a Chrome site, with only their Chrome patterns. One that also waits on another gate (for example a file outside the project for an upload) shows in the popup with "Answer it in Haarness", and the bridge refuses to answer it.

**Who cannot answer.**

- Client auto-repliers skip explicit requests: the TUI's `--yolo` and client-side Auto replies, `haarness run --yolo` and `workflow run --yolo` watchers, ACP, and Desktop's fallback auto-approver for older servers.
- `haarness run` at a terminal shows the call's arguments (the URL, script, text or files) and asks `[y] allow in this chat / [o] once / [N]`. Without a terminal it stops with "Stopped: the agent asked to use &lt;origin&gt; in Chrome, which always needs a person. Answer in the TUI or Desktop, or allow the site under Settings → Browser → Chrome."
- Scheduled runs, and the subagents, workflows and workflow agents they start, fail immediately, in turns and in a workflow's own tool calls: "Chrome needs the user's approval for &lt;origin&gt; and this run cannot ask. Ask the user to allow it in an interactive chat, then retry." Only the run counts as unattended: the first turn a schedule starts in the chat it created, and the work that turn starts (a workflow keeps it after the turn ends). A person who later types in that chat, runs `!` there or works in a fork of it is asked as usual. `--yolo` clients (the TUI, `haarness run`, ACP) and their workflow agents still ask.
- Requests scoped to a published chat (one shared with `/remote-control`, carrying `x-haarness-remote-thread`) answering an explicit prompt get 403 "Answer this on the computer running Chrome." A computer connected whole with `haarness remote enable` (Remote control › Hosts) relays unscoped requests with the local token, so an answer from there counts like one from a local client.

**API.** `PendingPermissionInfo.explicit` (`#[serde(default)]`) and the `permission.requested` event payload's `explicit: true` let clients tell these requests apart; both are in the OpenAPI document and the generated SDKs. Haarness browser `browser_site:` gates without the `chrome-` prefix behave as before.

## Extension budgets

In global or project `extensions.json`, keep `timeout_ms` as the fallback and override the stages that need more time:

```json
{
  "enabled": true,
  "timeout_ms": 30000,
  "init_timeout_ms": 60000,
  "hook_timeout_ms": 10000,
  "tool_timeout_ms": 0,
  "payload_max_bytes": 8388608,
  "entries": []
}
```

A deadline of `0` disables that deadline. Missing stage settings inherit `timeout_ms`; omitted project fields inherit global settings. The former five-minute maximum is removed. Message size defaults to 2 MiB and remains a positive configurable bound. Cancellation still terminates the host; timed-out or cancelled tools are not replayed. Large artifacts should normally be returned as files.

Haarness Cloud actions that spend money or replace or delete something (launching, messaging, scheduling, changing or deleting Cloud workspaces, templates and schedules) always ask, each time, with no **Always** choice; allow rules, `--yolo`, Auto approvals and hooks cannot skip the prompt, while a deny rule still refuses. A scheduled run, and the agents and workflows it starts, refuses such a request at once instead of waiting for a person: "'cloud_agent_manage:delete:…' needs the user's approval every time, and this scheduled run cannot ask. Do not retry it here; ask the user to do it in an interactive chat." The turn goes on with that refusal. See [Haarness account](HAARNESS-ACCOUNT.md). Chrome site approvals cannot be skipped that way either, but can be remembered for one chat; see [Chrome approvals](#chrome-approvals).

Generated media retains its existing approval default. Users who want it to run automatically can set `permission.media_generate` to `"allow"` in their existing ordered permission configuration. Browser transfer and diagnostic limits retain their existing bounds; they are separate from inline media reads.
