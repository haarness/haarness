# Remote computers through Haarness Cloud

> **User guide:** [Remote control](https://haarness.ai/docs/cloud/remote-hosts). This page has the engineering detail.

Use your own machine from Cloud web, the Cloud API, or the Python and TypeScript SDKs. The machine runs Haarness and makes an outbound authenticated WebSocket connection. No inbound port, SSH server, tunnel or Apple service is needed.

```sh
haarness login
cd /path/to/project
haarness remote enable --name "My computer"
haarness remote status
```

Open **Remote control › Hosts** in Cloud. Browse/open a folder, select a project, and work with its independent chats, shared files, approvals, model selection and terminal. The connector recovers when its local daemon restarts or changes address; while that daemon is starting, being replaced or too busy to answer, it waits 1 second, doubling to 30. It reconnects after a second when a connection that was up for a minute or carried a request ends, and it notices a stalled connection after 25 seconds without a word from Cloud (it pings every 5 seconds; a frame that cannot leave within 10 seconds counts too). Failed connects then wait at most 10 seconds for the first five minutes, since a computer that was connected most likely lost its network for a moment, and back off to a minute after that, or from the start when it never connected. After four connections in a row that Cloud accepts and drops at once it waits 1, 2, 4, 8 and then 10 minutes between attempts; a connection that went silent, or that Cloud took but did not say was ready within 10 seconds, counts as a failed connect, not as a drop, so a flaky network never reaches those waits. A Cloud outage or a network loss (Wi-Fi coming back after sleep) is waited out, including when the sign-in expires meanwhile and cannot be renewed: an unreachable Cloud, a 408, 429 or 5xx answer, or a page that is not Cloud's (a proxy's, a captive portal's) is retried on the same backoff. Only an answer no retry changes stops the connector: a refused or revoked sign-in or API key, revoked host access, or a relay protocol this version does not speak (it then says to update Haarness); `/remote-control` and `remote status` show that reason until the connector starts again. Its output says each way it fails once per outage (again every ten minutes while it lasts) instead of once per attempt, and the first connection that proves itself afterwards says `Remote host reconnected after N attempts in T`. Like HTTPS requests, the relay WebSocket (and Cloud's billing and update sockets) checks Cloud's certificate with the operating system's verifier, so a network that inspects TLS with a root the system trusts, such as a company proxy, works for remote control too. It uses the existing registered project daemons; it does not rent compute or copy the project into Cloud. Model calls still follow the provider and billing configuration on that computer.

`remote run` runs in the foreground and can be supervised by an OS service. `enable` starts a background process for the current login, not a boot/login startup service. Keep the machine awake. `remote disable HOST_ID` stops its connector without stopping accepted local work. `remote revoke HOST_ID` removes Cloud access. `remote forget HOST_ID` revokes and forgets a stopped local identity, allowing an explicit fresh registration. Host removal and project closing retain files and histories. A relayed request that fails on this computer reaches Cloud as a generic failure; the connector's output (the `remote-*.log` file beside its identity for a background connector) says why, naming the request by method and path only, never its query, headers or body.

To expose one conversation tree instead of project/terminal controls, type `/remote-control` (alias `/rc`) in that chat in the TUI or Desktop. The server's `remote-control` management resource (`start`, `stop`, `view`, `status`, each with `threadId`) starts the same background connector as `remote enable --chat`, waits until Cloud has published the chat (listed under **Remote control › Sessions**; the connector keeps its Cloud title in step with the chat's), and returns its link (`/app/remote/sessions/<publication>` on `HAARNESS_CLOUD_WEB_ORIGIN`, else the API origin) with a QR code as rows of modules. `/remote-control stop` stops the connector, unpublishes the chat, revokes its chat-only host and forgets the identity, so sharing again gets a fresh registration and link; sharing stopped from Cloud is detected the same way. Desktop marks a shared chat with a **Remote** chip beside the message box, read from `status` when the chat opens and again whenever Desktop's connection to the server comes back, since a share started or stopped meanwhile sends no event; an answer that a newer one or a start or stop in the dialog has overtaken is ignored. From a shell:

```sh
haarness remote enable --chat CHAT_ID --name "Shared investigation"   # background
haarness remote run --chat CHAT_ID --name "Shared investigation"      # foreground
```

Find the native chat ID in its URL or `haarness sessions list --json`. Attachments sent from Cloud clients may be images, PDFs, audio, video or text files (text is read into the message); other files are refused before the message is stored. Published chats include descendants and the project filesystem shared by all its chats; this is not a filesystem sandbox. The remote caller cannot enumerate/read/control other chat histories or host terminals. The machine checks this scope independently of the Cloud relay, and refuses publishing through an older runtime without scope enforcement.

## What waits on you

When Cloud lists `attention.v1` in the relay's `ready` frame, the connector tells it what waits on you, so Cloud can show it under **Needs you** and notify your phone without an open chat. A Cloud that does not list it receives nothing new (it would drop the connection on an unknown frame).

Each `attention` frame carries the complete set of pending approvals and questions (at most 200; Cloud resolves anything left out) and the chats whose turn finished, failed or was stopped in the last 15 minutes (`status` `completed`, `failed` or `interrupted`; at most 20, resent in every frame; Cloud keeps the first report of each turn). When Cloud also lists `attention.working` in `ready` (the connector asks for `attention.v1, attention.working` in `x-haarness-relay-features`), every frame carries `working` too: the root chats that have a turn running or background work still owing them a result (also before their first turn and after a stop), sorted, each once, at most 200. Without that feature the field is never sent, because a Cloud before it drops a frame with an unknown field. The first frame of every connection is sent even when nothing waits, once every running project has answered; after that a frame goes out only when something changed, at most every 300 ms, with a `revision` that grows within the connection.

Only this leaves the computer: the ids of the approval, question, turn and chats, the project's workspace id and name, the chat title, the approval's category (`bash`, `edit`, `webfetch`, `mcp` for any MCP tool, …), whether it is a Chrome approval, whether a question takes a free-text answer, whether a chat is a scheduled run, and times. Commands, paths, URLs, approval patterns and details, question text and anything the model wrote stay on the computer; a phone reads them through the relay when it opens the chat, which is where it answers.

The connector watches only project servers that already run. It finds them through their discovery records, as the Chrome bridge does, never through the host gateway, so it never starts, replaces or keeps a server running; a stopped server runs no turn, so nothing of it can wait on you. Projects closed for remote access are left out. A server started by a different Haarness build than the connector is reported with `actionable: false`: Cloud's request would have to replace it, which Haarness refuses while it is busy (a turn, an open terminal, a waiting approval or question, a running workflow), so it is answered on the computer. The project can still be viewed meanwhile: reads reach that server as it is, and anything else is refused with `409` `project_busy` ("This project is busy on a different version of Haarness. Open it on the computer, or wait until its work finishes."). A turn counts as finished only for the chat a person started, not a helper agent's, and only when the chat is quiet about two seconds later: no turn runs in it, so a goal, a loop, the next queued prompt or the reply to a stop that left steering unread carries on unreported, and of turns that end back to back only the last counts. A turn that completes or fails while work it started in the background (a child agent, a workflow run) still owes the chat a result is not reported either: that work delivers its result into the chat as a new turn, and the turn that receives the last result is the one reported. The connector reads this from the server's `GET /v1/threads/{id}/activity` and the `background` count of `turn.finished` (older servers have neither, and are judged by their running turn alone). A stopped root turn is reported as `interrupted` after the same check, whatever background work it leaves, since a stop cancels what the chat launched; Cloud stores it as stopped and never alerts for it. A chat held for background work can also go quiet with no further turn: it was stopped while idle, its last helper was stopped, the server stopped, or a result could not be delivered. The connector asks the server again a settle after a helper's `task.updated` says it ended, or a workflow run's status changes (`workflow.updated` is published on every log line, so only a start, pause, resume or end counts): an ended or paused run may leave its chat quiet (a paused run owes nothing until it is resumed), and a run that starts or resumes makes a quiet chat working again. It also asks every 30 seconds while a held chat runs no turn, and has at most one question about a chat on its way at a time. Background work a helper agent launched is the helper's: only root chats (or the published chat) are held, listed as working or reported. A reply read before a turn the connector already reported or is settling is ignored. While the chat is still owed, it stays held on the newest turn the server names, so stopping later work reports that turn. A chat still quiet a settle later is decided by the newest turn the server names (`lastTurn` of `/activity`): if it is the turn the chat was held on, that turn is reported as `interrupted`, once; if a newer turn ended meanwhile (the result arrived while its events were missed or not yet read), that turn is reported as it ended. Checks asked before the connector's event stream was reopened or resynced are discarded and asked again, so they never overtake events still to be read. A server without `lastTurn` cannot say which turn is the newest: there the held turn is reported unless events were missed since, in which case nothing is. The settle of a finished turn uses `lastTurn` the same way, so a turn found after missed events is never reported in place of a newer one that ended. Turns that ended before the connector started watching that server are not reported. A chat shared with `/remote-control` reports only its own chat tree, scoped by the server exactly as Cloud's requests to it are. The connector keeps reading its servers' events while Cloud is unreachable and between connections (an OAuth sign-in reconnects about every ten minutes), so a turn that finishes meanwhile is reported once it is connected again. When a server's events were missed anyway (the server keeps only its latest 2,048, and a streaming chat sends one per piece of text), the connector asks that server about the turns it last saw running, so their end is still reported; only a turn that started and ended entirely within the missed events goes unreported. The connector compares servers with the Haarness executable on disk at every scan, as the gateway does at every request, so after an in-place upgrade the servers the old build started are reported with `actionable: false`. Each scan reads the project registry as stored, without looking into project folders, and only when it or the closed projects changed.

## SDKs

```typescript
const cloud = new HaarnessCloud({ baseUrl: "https://haarness.ai", token });
const hosts = await cloud.listRemoteHosts();
const host = cloud.remoteHost(hosts.items[0].id);
const projects = await host.hostProjects();
const runtime = host.workspace(projects.workspaces[0].id);
const chat = await runtime.createThread({ provider: "haarness", model: "openai/gpt-4.1-nano" });
const result = await runtime.chat(chat.id, "Explain this project");
// cloud.remoteSession(publicationId) provides the scoped runtime directly.
// Native /v1 methods, events(), files and connectPty() use the relay.
runtime.close(); host.close(); cloud.close();
```

Python uses `remote_host(id).workspace(project_id)` and `remote_session(id)` on both `HaarnessCloud` and `AsyncHaarnessCloud`. CRUD methods for host/publication metadata are generated from the Cloud OpenAPI contract. Runtime credentials are resolved afresh for HTTP, events and PTYs; they never fall back to the local server token. Close runtime clients/streams when no longer needed. Native `/healthz` and `/openapi.json` are local discovery endpoints; remote runtime methods use `/v1`.

See the Cloud repository's `docs/REMOTE-ACCESS.md` for authorization, routing and deployment details and `skills/haarness-remote-access/SKILL.md` for verification.
